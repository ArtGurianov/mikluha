# TOUR-63 stage 1: direct S3 media

CUSTODY_IMPACT: NO until installed. No host/DB/provider changes or real-photo uploads are authorized by this source work. Sales remain CLOSED. Plane TOUR-63's 2026-10-30 scope governs: direct S3 completes this task; optional VPS-17 integration is a separate future task.

## Boundaries and selected approach

Keep the authenticated same-origin Control Room/Admin API and its separate database capability. A bounded JSON upload contains a client UUID/idempotency key, canonical base64 of at most 8 MiB JPEG/PNG/WebP, alt, credit and an explicit owned/consent rights reference and explicit confirmation covering recognizable-person consents. No client URL, bucket, key, arbitrary command or presigned browser PUT. OWNER/EDITOR can prepare; only a live OWNER session can publish or revoke.

Use a bounded PostgreSQL staging queue and a separate media worker login/process. This keeps S3 keys and image decoding out of Admin and the public site. Staging bytes are private temporary data (also subject to encrypted DB-backup retention), cleared after processing or withdrawal. A direct Admin-to-S3 implementation would breach the existing no-S3-credential Admin contract; browser presigned public uploads would bypass admission. No root/publisher/Docker credentials are introduced into Control Room.

The worker processes one asset under its row lock, serializing publication/deletion with state changes. Private original and deterministic immutable per-asset variant keys are fixed by server UUID/source hash/profile. Write-once admission and full read-back precede readiness. Variants are private while READY; OWNER publish requests public ACL only for processed WebP. Anonymous exact-byte/MIME/cache verification precedes PUBLISHED. Fixed deterministic keys let withdrawal clean partially completed work after a crash. Missing/error acknowledgements never mean success.

A credential-free decoder container with no IP network accepts byte requests over a shared Unix socket; the worker mounts only this socket read-only and holds no image parser. Its bounded Python/Pillow subprocess accepts only JPEG/PNG/WebP, at most 8 MiB/16 Mpixels/8192 per side, one frame. It applies orientation, strips metadata by copying decoded pixels into fresh images, and emits WebP variants at 480/960/1600 without upscaling. Linux resource limits bound address space, CPU, file size/open files; the Node parent applies a wall deadline, sanitized environment and output bounds. Both containers have explicit RAM/CPU/PID caps, the decoder has bounded tmpfs, and neither receives a Docker socket or capabilities. Pillow is pinned; malformed files, polyglot/metadata issues and bombs are tested in the actual process.

## Public content, revocation and recovery

Editorial documents use media:<UUID> references. Commerce resolves only PUBLISHED media within the same read-only projection snapshot; private keys, upload bytes, rights references and unpublished assets never enter public DTOs. An unresolved/revoked image reference becomes the tracked neutral local placeholder, never an origin guess; this preserves required-cover SSR normalization. Plain text is never rewritten. The SSR site renders direct approved HTTPS S3 WebP URLs with native img, no runtime transform or CDN substitution. Control Room media upload/status/OWNER publish/revoke is a small first-party flow; general content editors stay TOUR-64.

Withdrawal first removes DB public eligibility, then the worker deletes all four deterministic keys and verifies anonymous absence; only then REVOKED. Browser cache is short (60 seconds, must-revalidate), with documented already-delivered/in-flight limitations; immutable keys mean immutable bytes, not year-long browser retention. Database/backup copies, rights evidence and old object versions require explicit retention/erasure policy; no false claim of physical backup erasure. New buckets must be private-by-default with object-level public processed access, versioning disabled for this contract, constrained IAM, HTTPS/CORS/cache and independent provider tests. Replay after restore must reconcile latest revocations before publishing; do not blindly replay a historical public ACL.
