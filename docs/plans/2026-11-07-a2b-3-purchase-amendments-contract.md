(`purchase_revision`, как в 0017/0021). Поправка без ревизии договор не меняет, ревизия без поправки (кроме `INITIAL`) не

## 0. Что решает A2b-3 и чего не делает

| Вопрос | Решение |
|---|---|
| Что это | Общий **механизм** изменения уже существующей покупки: предложение → согласие по хэшу → атомарная ревизия → деньги по реестру 0026. Не «универсальный движок ревизий» (TOUR-75): закрытый список оснований, у каждого своя команда, свои предусловия и своё правило цены |
| Основания в A2b-3 | `TICKET_TYPE_CORRECTION`, `PARTICIPANT_REPLACEMENT`, `PARTIAL_CANCELLATION`, `FULL_TERMINATION`, `DEPARTURE_TRANSFER` (трек E, TOUR-79) |
| Основания других этапов | `TERMS_REACCEPTANCE` — A2b-10; `DEPARTURE_CHANGE_ACCEPTANCE` и `DEPARTURE_CHANGE_INFORMED` — TOUR-89/92. Значения и места в матрицах резервируются здесь, а включают их миграции этих этапов |
| Вне механизма | Добавление участника — отдельная покупка группы (OWNER 04.11 «д», TOUR-90). Первая персонализация пустого места — не поправка (v1.8.2 §2.3). Исправление ПД того же лица — `participants.pd.correct`, без ревизии. Продление срока долга — отдельное событие без ревизии (MK-C01). Смена заказчика и замена с переходом в другую категорию — вне штатного потока (TOUR-79) |
| Что даёт A2b-3 для TOUR-89 | Блокировку новых платежей, пока покупатель не согласился на существенное изменение (§18, вход ревью GPT), и одну модель обязательства: обязательство TOUR-89 по покупке — это поправка с основанием `DEPARTURE_CHANGE_ACCEPTANCE` (§9) |

## 2. Жизненный цикл: предложение → согласие → ревизия

### 2.1. Порядок

1. **Создание** (`fn_amendment_propose_<basis>`): блокировки по §7. Проверка предусловий основания (§4) по
   текущей ревизии. Построение кандидата: строка на **каждое** место покупки с итоговыми типом, ценой, статусом строки,
   выездом, а также денежный снимок §5.2. Запись `candidate_hash`. Повтор с тем же `idempotency_key` и тем же запросом
   возвращает ту же поправку; тот же ключ с другим запросом — `IDEMPOTENCY_CONFLICT`.
2. **Согласие** (`fn_amendment_consent(amendmentRef, candidateHash, канал)`): только POST с хэшем, который видел
   покупатель. GET, переход по ссылке, сканер почты согласием не являются. БД заново строит кандидат по текущему
   состоянию. Если хэш не совпал — `AMENDMENT_STALE`, поправка закрывается `STALE`.
3. **Вступление** (`fn_amendment_commit`, внутренняя): в той же транзакции, что согласие, если
   `requires_payment_kopecks = 0`. Иначе — при применении успешной операции `AMENDMENT` (§5.4). Ревизия, её строки,
   смена состояний мест, перераспределения §5.3, заявки урегулирования §5.5 и закрытие поправки записываются атомарно.
   При любом отказе не меняется ничего.
4. **Записи сотрудника** (`consent_mode = STAFF_RECORDED`, §4): создание и вступление — одна команда, состояния `OPEN`
   нет.

### 2.2. Хэш кандидата

`candidate_hash` вычисляет БД из канонического JSON. Входят:
- `purchaseRef`, `basis`;
- `base_revision` и `base_revision_hash`;
- выезд и версия выезда до и после;
- строки кандидата в порядке `position`: `seatSlotRef`, статус строки, тип билета, цена, `pricingBasisRef`;
- итог и число активных мест;
- сроки `deposit_until` / `balance_due_at`, которые будут у ревизии;
- денежный снимок §5.2 на каждое место;
- `requires_payment_kopecks`;
- ссылка и хэш правовых текстов, которые принимает покупатель (договор v2, дополнение TOUR-89, оферта, согласие на ПД);
- `expires_at`.

Аудит, время создания и повторные callbacks в хэш не входят. Изменение любого входа делает кандидата устаревшим: старое
согласие не переносится на новый кандидат (02 §9.2, MK-POLICY §5).

### 2.3. Ревизия поправки

| Колонка | Правило |
|---|---|
| `basis` | основание поправки; `CHECK` расширяется закрытым списком §0 |
| `amendment_id` | `UNIQUE`; NOT NULL ⇔ основание не `INITIAL`/`QUOTE_REPLACEMENT` |
| `document_order_id` | NOT NULL только для `INITIAL`/`QUOTE_REPLACEMENT`. Документ поправки — её кандидат и принятые правовые тексты; контакт покупателя не дублируется (A2b-10 §2 п.2), закрытие и удаление по 8B остаются на документе-заказе |
| `departure_id`, `departure_version` | из кандидата (меняют только перенос и изменение выезда) |
| `seats`, `total_kopecks` | число и сумма **активных** строк; 0 допустим только у `FULL_TERMINATION` (ограничения 0017/0021 `seats ≥ 1`, `total > 0` заменяются условными) |
| `legal_release_*`, `pd_consent_*`, `contract_snapshot_sha256` | принятые в согласии; у `STAFF_RECORDED` — копия предыдущей ревизии |
| `accepted_at` / `effective_at` | время согласия / время вступления (БД) |
| `deposit_until`, `balance_due_at` | **замороженные сроки ревизии** (§5.6) |
| `predecessor_hash`, `revision_hash` | как в 0017/0021; в хэш добавляются `amendmentRef`, `candidateHash`, сроки. Хэши прежних ревизий пересчитываются без изменений (те же ключи JSON) |

Строки ревизии: по одной на **каждое** место покупки, включая отменённые ранее (`line_status = CANCELLED`, цена —
последняя договорная, в сумму не входит). `lines_sha256` включает `line_status`. Правило цены строки зависит от основания
(§4, столбец «Цена»); проверяет триггер строки, а не вызывающий.

## 3. Матрица состояний поправки

```
            согласие (без оплаты) / запись сотрудника ─────────────────────────────► COMMITTED
  OPEN ──┬─ согласие + операция AMENDMENT ── SUCCEEDED, вступление возможно ──────► COMMITTED
         │                                 └ SUCCEEDED, вступление невозможно ─► NEEDS_RESOLUTION ─(заявка решена)─► CLOSED(SETTLED)
         ├─ отзыв сотрудником / отказ покупателя / срок / устарела / вытеснена ─────► CLOSED(<причина>)
         └─ операция FAILED ───────────────────────────────────────────────────────► CLOSED(PAYMENT_FAILED)
```

Отдельных состояний `CONSENTED` / `PAYMENT_PENDING` нет: согласие — факт (`purchase_amendment_consent`), платёж — статус
своей `bank_operation` (02 §9.2).

| Событие ↓ / состояние → | `OPEN`, согласия нет | `OPEN`, согласие есть, операции нет | `OPEN`, операция `AMENDMENT` в полёте (`INTENDED`/`REGISTERED`/`UNKNOWN` или `application_due`) | `NEEDS_RESOLUTION` | `COMMITTED` / `CLOSED` |
|---|---|---|---|---|---|
| Согласие с актуальным хэшем | вступление (если оплата не нужна) или запись согласия | повтор: тот же `consentRef` | повтор: тот же `consentRef` | `AMENDMENT_NOT_OPEN` | повтор того же согласия возвращает итог; иначе `AMENDMENT_NOT_OPEN` |
| Согласие с другим хэшем / база изменилась | `AMENDMENT_STALE` → `CLOSED(STALE)` | невозможно: база заморожена блокировками §6 | невозможно | `AMENDMENT_NOT_OPEN` | `AMENDMENT_NOT_OPEN` |
| Отказ покупателя | `CLOSED(REJECTED)` | `CLOSED(REJECTED)` | `AMENDMENT_PAYMENT_IN_FLIGHT` | — | `AMENDMENT_NOT_OPEN` |
| Отзыв сотрудником (`amendment.record`, причина) | `CLOSED(WITHDRAWN)` | `CLOSED(WITHDRAWN)` | `AMENDMENT_PAYMENT_IN_FLIGHT` | — | `AMENDMENT_NOT_OPEN` |
| Срок истёк (`maintain`, часы БД) | `CLOSED(EXPIRED)` | `CLOSED(EXPIRED)` | **не закрывается**: ждёт исхода банка, срок не снимает UNKNOWN | — | — |
| Открыть операцию `AMENDMENT` | `AMENDMENT_CONSENT_REQUIRED` | одна операция; повтор возвращает её | повтор возвращает её | `AMENDMENT_NOT_OPEN` | `AMENDMENT_NOT_OPEN` |
| Операция `SUCCEEDED`, вступление возможно | — | — | `COMMITTED`, деньги распределены по кандидату | — | поздний успех после `CLOSED` → заявка `AMENDMENT_LATE_PAYMENT` |
| Операция `SUCCEEDED`, вступление невозможно (нет места, T−24 цели, база изменилась) | — | — | `NEEDS_RESOLUTION` + заявка `AMENDMENT_UNCOMMITTABLE`; деньги не гасят старый долг | — | — |
| Операция `FAILED` | — | — | `CLOSED(PAYMENT_FAILED)`; новый платёж — только новая поправка | — | — |
| Заявка урегулирования решена (возврат или решение OWNER) | — | — | — | `CLOSED(SETTLED)` | — |
| Вступила другая ревизия той же покупки | `CLOSED(STALE)` | невозможно (§6, I-12) | невозможно | — | — |
| TOUR-89: новая редакция C при открытом обязательстве к B | `CLOSED(SUPERSEDED)` + новое обязательство к C | то же | то же | — | — |
| Перенос или прекращение вступили при открытом обязательстве TOUR-89 | `CLOSED(RESOLVED_BY_OTHER)`, исход записывается (§9) | то же | — | — | — |

`closed_reason`: `REJECTED`, `WITHDRAWN`, `EXPIRED`, `STALE`, `SUPERSEDED`, `RESOLVED_BY_OTHER`, `PAYMENT_FAILED`,
`SETTLED`. На покупку одновременно открыто не больше **одной** поправки сотрудника и не больше **одного** обязательства
TOUR-89 (частичные уникальные индексы).

### 3.1. Состояния места: что добавляет A2b-3

К матрице §3 контракта трека A добавляется только переход `CONFIRMED → CANCELLED`. Триггер `seat_slot` разрешает его,
только если в этой же транзакции вставлена ревизия с основанием `PARTIAL_CANCELLATION` / `FULL_TERMINATION` /
`DEPARTURE_TRANSFER` (частичный перенос, §4) и строка этого места в ней `CANCELLED`. Обратного перехода нет.

| Состояние места | Можно ли менять поправкой |
|---|---|
| `CONFIRMED` | да, всеми основаниями A2b-3 |
| `HELD`, `RELEASED` (неоплаченная покупка) | только `TERMS_REACCEPTANCE` (A2b-10). Основания A2b-3 — `AMENDMENT_PURCHASE_NOT_CONFIRMED` |
| `PAID_NO_SEAT_EXCEPTION` | нет: сначала назначение места или возврат (TOUR-27) — `AMENDMENT_SEAT_NOT_ELIGIBLE` |
| `REFUND_SETTLED`, `CANCELLED` | конечные; строка переносится в следующую ревизию без изменений |

### 3.2. Состояние покупки × основание

Состояние покупки выводится, а не хранится.

| Основание ↓ / состояние покупки → | Не оплачена, места `HELD`/`RELEASED` | Подтверждена, долг или оплачена полностью | Операция в полёте или `application_due` | Открыта заявка урегулирования (кроме `PAID_NO_SEAT`) | Открыто обязательство TOUR-89 без согласия | Все места отменены | Закрыта по 8B |
|---|---|---|---|---|---|---|---|
| `TICKET_TYPE_CORRECTION` | `AMENDMENT_PURCHASE_NOT_CONFIRMED` | ✔ | `AMENDMENT_PAYMENT_IN_FLIGHT` | `AMENDMENT_SETTLEMENT_PENDING` | `DEPARTURE_CHANGE_UNRESOLVED` | `AMENDMENT_PURCHASE_TERMINATED` | `PURCHASE_CLOSED` |
| `PARTICIPANT_REPLACEMENT` | то же | ✔ | то же | ✔ (деньги не затрагивает) | `DEPARTURE_CHANGE_UNRESOLVED` | то же | то же |
| `PARTIAL_CANCELLATION` | то же | ✔ | то же | то же | ✔ (одно из средств покупателя) | то же | то же |
| `FULL_TERMINATION` | то же | ✔ | то же | то же | ✔, обязательство закрывается `RESOLVED_BY_OTHER` | то же | то же |
| `DEPARTURE_TRANSFER` | то же | ✔ | то же | то же | ✔, обязательство закрывается `RESOLVED_BY_OTHER` | то же | то же |
| `TERMS_REACCEPTANCE` (A2b-10) | ✔ только `RELEASED`, в окне 24 ч / T−24 | — | то же | то же | — | — | то же |
| `DEPARTURE_CHANGE_ACCEPTANCE` (TOUR-92) | — (неоплаченным покупкам — отказ 0025 и `TERMS_REACCEPTANCE`) | ✔ | согласие допустимо, вступление ждёт исхода операции (§9) | ✔ | — | — | то же |

«Операция в полёте» — любая `COLLECTION` или `REFUND` покупки в `INTENDED`/`REGISTERED`/`UNKNOWN` или с
`application_due`, кроме операции `AMENDMENT` этой же поправки. Банковская неопределённость останавливает изменение
состава и денег, срок предложения её не снимает (TOUR-79, MK-POLICY §2 п.5).

## 5. Деньги: интеграция с реестром 0026

### 5.1. Определения (на место, по текущей ревизии)

| Величина | Формула |
|---|---|
| `price` | цена строки текущей ревизии (для `CANCELLED` — последняя договорная, только справочно) |
| `received` | Σ `seat_money_allocation` места + Σ входящих `seat_money_transfer` − Σ исходящих |
| `refunded` | Σ `bank_refund_allocation` места |
| `net` | `received − refunded` (≥ 0, I-8) |
| `due` | для активной строки `max(0, price − net)`; для `CANCELLED` — 0 |
| `excess` | для активной строки `max(0, net − price)`; для `CANCELLED` — `net` |

0026 считает `balance_due = price − paid` без возвратов и перераспределений: до 0026 возвраты были только по «оплате без
места». A2b-3 заменяет представления `seat_money` / `purchase_money` этими формулами. Охрана
`fn_seat_money_allocation_guard` сравнивает с ценой `net + amount`, а не валовую сумму. В отменённое место деньги не
распределяются.

### 5.2. Денежный снимок кандидата

На каждое место в хэш кандидата входят `price` до и после, `net`, `due` и `excess` после вступления, а также
перераспределения §5.3. Любое новое распределение, возврат или операция по покупке меняют снимок: несогласованная
поправка устаревает (`AMENDMENT_STALE`). Так «новый сторонний платёж делает предложение устаревшим» (02 §9.2).
Согласованная поправка снимок не теряет: после согласия новые обычные платежи запрещены (§5.7).

### 5.3. Перераспределение внутри покупки

При вступлении `excess` **активных** мест детерминированно переносится на `due` других активных мест той же покупки:
источники и получатели по возрастанию `position`, наибольший перенос первым. Каждая запись `seat_money_transfer` содержит
поправку, место-источник, место-получатель и сумму; записи только добавляются. Так покрываются правила 02 §9.3:
переплата одного места гасит долг другого, а более дешёвая поездка сокращает остаток без возврата. Перенос с отменённых
мест на активные **по умолчанию не делается**: размер законного возврата за отменённое место определяется отдельно
(MK-POLICY §3); вопрос Q3. Между покупками деньги не переносятся никогда.

### 5.4. Оплата до вступления (`purpose = AMENDMENT`)

- Новое значение `bank_operation.purpose`. Операция ссылается на `amendment_id`, а не на цикл; сумма равна
  `requires_payment_kopecks`. Открыть её можно только после согласия и до `expires_at` с техническим запасом на
  регистрацию в банке (MK-POLICY §2 п.6). На поправку — одна операция; повтор возвращает её.
- При `SUCCEEDED` применение (`fn_bank_operation_apply_locked`) вызывает вступление. Деньги распределяются **по
  кандидату** (на `due` после вступления) в той же транзакции, что ревизия. Если вступление невозможно — `NEEDS_RESOLUTION`
  и заявка `AMENDMENT_UNCOMMITTABLE`. Деньги остаются фактом операции и **не гасят старый долг** (02 §9.2, TRANSFER-PAY-03).
- При `FAILED` — `CLOSED(PAYMENT_FAILED)`. Места и деньги не меняются.

### 5.5. Заявки урегулирования (TOUR-27): новые причины

| Причина | Когда | Максимум к возврату |
|---|---|---|
| `AMENDMENT_OVERPAYMENT` | после §5.3 у активных мест остался `excess` | Σ `excess` активных мест |
| `CANCELLATION_SETTLEMENT` | частичная отмена или прекращение с `net > 0` у отменённых мест | Σ `net` отменённых мест |
| `AMENDMENT_UNCOMMITTABLE` | оплата `AMENDMENT` успешна, вступление невозможно | сумма операции |
| `AMENDMENT_LATE_PAYMENT` | успех `AMENDMENT` после закрытия поправки | сумма операции |

Решает сотрудник с `refund.execute` (OWNER): `REFUNDED` (возврат через `fn_bank_refund_open` с распределением на
места) или `OWNER_DECISION` с причиной, в том числе нулевой возврат при доказанных расходах. Заявка, открытая на покупку,
блокирует новые `BALANCE` (0026, `BALANCE_SETTLEMENT_PENDING`) и новые поправки (§3.2).

### 5.6. Сроки долга замораживаются в ревизии

0026 вычисляет `deposit_until` / `balance_due_at` по **живому** выезду. После TOUR-89 правка расписания сдвигала бы старый
долг, а v1.8.2 §7.1 это запрещает. A2b-3 записывает оба срока в ревизию:
- `INITIAL` — от выезда на момент создания;
- поправка — копия предыдущей ревизии;
- новые сроки — только по согласию в кандидате (перенос, `DEPARTURE_CHANGE_ACCEPTANCE`);
- продление долга менеджером — отдельное событие MK-C01, без ревизии (вне A2b-3).

Окно оплаты остатка в `fn_bank_operation_open_payment` проверяется по сроку текущей ревизии. Для **новых допусков**
(цикл, депозит, перенос) при неурегулированном изменении расписания действует защитная граница `min(старое, новое)`
(v1.8.2 §7.1). У ревизий, созданных до этой миграции (только синтетика), сроков нет: они вычисляются как в 0026.

### 5.7. Матрица открытия платежа (дополняет 0026)

| Состояние покупки | `FULL` / `DEPOSIT` (цикл) | `BALANCE` | `AMENDMENT` |
|---|---|---|---|
| Нет поправок | как 0025/0026 | как 0026 | `AMENDMENT_NOT_OPEN` |
| Открыта поправка без согласия | как 0026; платёж делает её устаревшей | как 0026; то же | `AMENDMENT_CONSENT_REQUIRED` |
| Открыта поправка с согласием | `AMENDMENT_IN_PROGRESS` | `AMENDMENT_IN_PROGRESS` | одна операция, повтор возвращает её |
| `NEEDS_RESOLUTION` | `AMENDMENT_SETTLEMENT_PENDING` | `AMENDMENT_SETTLEMENT_PENDING` (и 0026 `BALANCE_SETTLEMENT_PENDING`) | `AMENDMENT_NOT_OPEN` |
| Открыто обязательство TOUR-89 режима `CONSENT`, покупатель ещё не согласился | `DEPARTURE_CHANGE_UNRESOLVED` (для неоплаченных уже действует 0025 `DEPARTURE_CHANGED`) | **`DEPARTURE_CHANGE_UNRESOLVED`** — вход §18 | — |

## 7. Блокировки и конкуренция

**Глобальный порядок** для всех путей: платёж, повторный цикл, закрытие, применение исхода банка, поправка, публикация
выезда:

1. выезды, `FOR UPDATE`, по возрастанию `departure.id`: текущий выезд покупки и, для переноса, цель;
2. строка документа-заказа покупки;
3. строка `purchase`;
4. открытый цикл (`seat_hold`);
5. места по возрастанию `position`;
6. операции покупки по возрастанию `id`.

Это продолжение порядка 0021/0022/0025: выезд → документ-заказ → цикл → места. Переносу нужны два выезда: их порядок по
`id` исключает взаимную блокировку двух встречных переносов.

| Гонка | Результат |
|---|---|
| Два переноса на последнее место цели | первый вступает; второй при вступлении получает `NOT_ENOUGH_SEATS`, его исходные места не освобождены |
| Перенос и обычная покупка на последнее место цели | сериализуются на строке цели; проигравший получает `NOT_ENOUGH_SEATS` |
| Согласие на поправку и `BALANCE` по той же покупке | `BALANCE` первым: снимок изменился → `AMENDMENT_STALE`. Согласие первым: `BALANCE` → `AMENDMENT_IN_PROGRESS` |
| Применение успеха `BALANCE` и вступление поправки | вступление проверяет I-11 под блокировкой операций: ждёт применения, затем снимок другой → `AMENDMENT_STALE` |
| Публикация новой редакции выезда и вступление переноса на него | сериализуются на строке выезда. Перенос, начатый до публикации, вступает на версии из кандидата, если она ещё текущая; иначе `DEPARTURE_CHANGED` |
| Две вкладки согласия | одна запись согласия (`UNIQUE`); вторая получает тот же `consentRef` |
| `maintain` закрывает поправку по сроку и одновременно приходит согласие | сериализуются на строке поправки; согласие после `CLOSED` — `AMENDMENT_NOT_OPEN` |

Внешний банковский вызов всегда вне транзакции вступления (02 §7.2).

| Согласие покупателя | только сессия покупателя (0023) или одноразовая ссылка поправки; у Admin API пути нет |

Каждая CR-команда проверяет `fn_staff_permitted` в БД.

## 9. TOUR-89/92: изменение проданного выезда

1. Публикация изменённой версии выезда с договорными полями (TOUR-92) создаёт по каждой затронутой покупке
   обязательство — поправку `DEPARTURE_CHANGE_ACCEPTANCE` с режимом:
   - `CONSENT` — `BUYER_HASH` по `appendixHash`;
   - `INFORM` — `INFORMED`, только при правовом основании TOUR-84.

   Каждая покупка группы — отдельно (v1.9.0 §8).
2. Базовая редакция покупки — выезд и версия её текущей ревизии. Новая редакция C при открытом обязательстве к B
   закрывает его `SUPERSEDED` и открывает обязательство к C. Ссылки на B устаревают, операторские задачи по B
   остаются (v1.8.2 §7 п.4, п.10).
3. Пока обязательство `CONSENT` открыто, действуют I-13 и §5.7: новые платежи по покупке запрещены. Уже
   зарегистрированная операция завершается на условиях своей регистрации (v1.9.1 §4 п.2).
4. 72 часа — срок внимания оператора, а не акцепт. Обязательство без согласия по сроку **не закрывается**: у него нет
   `expires_at`.
5. Исходы для покупателя:
   - согласие → ревизия `DEPARTURE_CHANGE_ACCEPTANCE`;
   - перенос → `DEPARTURE_TRANSFER`, обязательство закрывается `RESOLVED_BY_OTHER`, исход `TRANSFERRED`;
   - полный возврат → `FULL_TERMINATION` с причиной `ORGANIZER_CHANGE`, исход `REFUNDED`.

   Исход договора (`contractDisposition`) и операторская задача — независимые оси (v1.8.2 §7 п.8). Задача — TOUR-92/102,
   не A2b-3.
6. Покупка с операцией в полёте: согласие записывается, вступление ждёт исхода операции (I-11).

## 10. План миграций и приёмка

Номера назначает единый владелец DDL по журналу. 0001–0026 не меняются.

| Миграция | Содержание |
|---|---|
| **0027 · A2b-3a** | Механизм: таблицы §1; основания `TICKET_TYPE_CORRECTION`, `PARTICIPANT_REPLACEMENT`, `PARTIAL_CANCELLATION`, `FULL_TERMINATION`; переход `CONFIRMED → CANCELLED`; ревизии без документа-заказа; замороженные сроки §5.6; `net`/`due`/`excess`, `seat_money_transfer`, новые причины заявок; `fn_purchase_payment_blocker` в `fn_bank_operation_open_payment`; права |
| **0028 · A2b-3b** | `DEPARTURE_TRANSFER`: два выезда в блокировках, новая основа цены цели, проверка ёмкости при вступлении, `purpose = AMENDMENT`, `NEEDS_RESOLUTION`, ссылка согласия |
| A2b-10 | `TERMS_REACCEPTANCE` на этом механизме |
| TOUR-92 | обязательства `DEPARTURE_CHANGE_*`, пакеты уведомлений, снятие date-lock после приёмки |

Разделение на 0027/0028 позволяет ревьюировать перенос (ёмкость и оплата до вступления) отдельно от остальных оснований.

**Приёмка 0027 (синтетика, PG16):**
- Исправление 0–13 → 18+ по собственной сетке места: исходная покупка 10 000 / 15 000 → долг 5 000; место с другой
  основой — по своей сетке (v1.8.2 §2.3).
- Снижение цены: примеры v1.8.2 §2.3 — 20 000 → 10 000 при полученных 5 000 / 15 000 / 20 000 → долг 5 000 /
  переплата 5 000 / 10 000. Переплата одного места гасит долг другого той же покупки, остаток — `AMENDMENT_OVERPAYMENT`.
- Частичная отмена: место `CANCELLED`, занятость освобождена, заявка `CANCELLATION_SETTLEMENT` на `net`, решение с нулевым
  возвратом допустимо. Последний взрослый с детьми — `MINORS_WITHOUT_ADULT`. Выбытие сопровождающего отзывает назначение.
- Прекращение: `seats = 0`, `total = 0`, `NOTHING_DUE` на все платежи.
- Устаревание: поправка → `BALANCE` → согласие `AMENDMENT_STALE`; согласие → `BALANCE` `AMENDMENT_IN_PROGRESS`; две
  поправки подряд — вторая вступает только на новой базе.
- UNKNOWN: операция покупки в полёте → создание и вступление отклонены. Срок не закрывает поправку с операцией в полёте.
- Повтор: создание и согласие с тем же ключом возвращают тот же результат. Прямой DML любого сервисного логина не
  создаёт ревизию поправки, не отменяет место и не меняет реестр.
- I-10 сходится после каждого шага всех сценариев.
- Хэши ревизий 0017/0021 пересчитываются без изменений. Сроки ревизии не меняются при правке расписания выезда
  суперпользователем.

**Приёмка 0028:**
- Конкурентные переносы на последнее место в обоих порядках.
- Перенос и покупка на последнее место.
- Встречные переносы A→B и B→A без взаимной блокировки.
- Перенос дороже и дешевле (02 §9.3: 80 000 / внесено 20 000 → 70 000 → долг 50 000; полная 80 000 → 70 000 →
  переплата 10 000).
- Оплата до вступления: успех → вступление; успех без места → `NEEDS_RESOLUTION`, деньги не в старом долге; отказ →
  `PAYMENT_FAILED`.
- Срок предложения ≤ 6 ч; T−24 цели.

## 11. Вопросы OWNER (до 0027)

Предложение по умолчанию указано; без ответа оно применяется только к синтетике и проходит ревью.

| № | Вопрос | Предложение |
|---|---|---|
| Q1 | Пока покупатель не ответил на существенное изменение TOUR-89, а срок остатка наступает — что со сроком? | Ничего автоматически: платёж заблокирован (I-13), просрочка ничего не отменяет (MK-C03). Новый срок — в согласии или отдельным продлением MK-C01; оператор видит покупку в задаче TOUR-89 |
| Q2 | Нужно ли согласие покупателя на исправление категории, которое только **снижает** цену? | Нет: `STAFF_RECORDED` с уведомлением и заявкой на переплату. Повышение — только `BUYER_HASH` |
| Q3 | Засчитывать ли деньги отменённого места в долг оставшихся мест той же покупки? | Не автоматически: сумма возврата за отменённое место определяется отдельно (MK-POLICY §3). Зачёт — решение в заявке `CANCELLATION_SETTLEMENT` (`OWNER_DECISION`), записывается перераспределением с причиной |
| Q4 | Частичный перенос (часть мест покупки на другой выезд)? | Вне запуска: переносятся все активные места. Иначе — частичная отмена + новая покупка группы |
| Q5 | Перенос покупки, состоящей в группе из нескольких покупок? | Вне запуска (`GROUP_TRANSFER_NOT_SUPPORTED`): детские покупки группы зависят от взрослого на том же выезде (v1.9 §3). Ручной путь — по покупке через прекращение и новую покупку |
| Q6 | Срок согласия на поправки, кроме переноса? | 72 ч, не позже T−24 выезда; перенос — 6 ч (MK-POLICY §6) |
