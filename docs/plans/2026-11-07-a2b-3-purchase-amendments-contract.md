Термины. **Поправка** (`purchase_amendment`) — предложение изменить покупку; **ревизия** — принятый результат

## 0. Что решает A2b-3 и чего не делает

| Вопрос | Решение |
|---|---|
| Что это | Общий **механизм** изменения уже существующей покупки: предложение → согласие по хэшу → атомарная ревизия → деньги по реестру 0026. Не «универсальный движок ревизий» (TOUR-75): закрытый список оснований, у каждого своя команда, свои предусловия и своё правило цены |

| Основания других этапов | `TERMS_REACCEPTANCE` — A2b-10; `DEPARTURE_CHANGE_ACCEPTANCE` и `DEPARTURE_CHANGE_INFORMED` — TOUR-89/92. Значения и места в матрицах резервируются здесь, а включают их миграции этих этапов |

| Что даёт A2b-3 для TOUR-89 | Блокировку новых платежей, пока покупатель не согласился на существенное изменение (§18, вход ревью GPT), и одну модель обязательства: обязательство TOUR-89 по покупке — это поправка с основанием `DEPARTURE_CHANGE_ACCEPTANCE` (§9) |

## 2. Жизненный цикл: предложение → согласие → ревизия

### 2.1. Порядок

1. **Создание** (`fn_amendment_propose_<basis>`): блокировки по §7. Проверка предусловий основания (§4) по
   текущей ревизии. Построение кандидата: строка на **каждое** место покупки с итоговыми типом, ценой, статусом строки,
   выездом, а также денежный снимок §5.2. Запись `candidate_hash`. Повтор с тем же `idempotency_key` и тем же запросом
   возвращает ту же поправку; тот же ключ с другим запросом — `IDEMPOTENCY_CONFLICT`.
2. **Согласие** (`fn_amendment_consent(amendmentRef, candidateHash, канал)`): только POST с хэшем, который видел
   покупатель. GET, переход по ссылке, сканер почты согласием не являются. БД заново строит кандидат по текущему
   состоянию. Если хэш не совпал или срок истёк, поправка закрывается (`STALE` / `EXPIRED`), и это закрытие
   сохраняется (§2.4).
3. **Вступление** (`fn_amendment_commit`, внутренняя): в той же транзакции, что согласие, если
   `requires_payment_kopecks = 0`. Иначе — при применении успешной операции `AMENDMENT` (§5.4). Ревизия, её строки,
   смена состояний мест, перераспределения §5.3, заявки урегулирования §5.5 и закрытие поправки записываются атомарно.
   При любом отказе не меняется ничего.
4. **Записи сотрудника** (`consent_mode = STAFF_RECORDED`, §4): создание и вступление — одна команда, состояния `OPEN`
   нет.

### 2.2. Хэш кандидата

`candidate_hash` вычисляет БД из канонического JSON. Входят:
- `purchaseRef`, `basis`;
- `base_revision` и `base_revision_hash`;
- выезд и версия выезда до и после;
- строки кандидата в порядке `position`: `seatSlotRef`, статус строки, тип билета, цена, `pricingBasisRef`;
- итог и число активных мест;
- сроки `deposit_until` / `balance_due_at`, которые будут у ревизии;
- денежный снимок §5.2 на каждое место;
- `requires_payment_kopecks`;
- ссылка и хэш правовых текстов, которые принимает покупатель (договор v2, дополнение TOUR-89, оферта, согласие на ПД);
- `expires_at`.

Аудит, время создания и повторные callbacks в хэш не входят. Изменение любого входа делает кандидата устаревшим: старое
согласие не переносится на новый кандидат (02 §9.2, MK-POLICY §5).

### 2.3. Ревизия поправки

| Колонка | Правило |
|---|---|
| `basis` | основание поправки; `CHECK` расширяется закрытым списком §0 |
| `amendment_id` | `UNIQUE`; NOT NULL ⇔ основание не `INITIAL`/`QUOTE_REPLACEMENT` |
| `document_order_id` | NOT NULL только для `INITIAL`/`QUOTE_REPLACEMENT`. Документ поправки — её кандидат и принятые правовые тексты; контакт покупателя не дублируется (A2b-10 §2 п.2), закрытие и удаление по 8B остаются на документе-заказе |
| `departure_id`, `departure_version` | из кандидата (меняют только перенос и изменение выезда) |
| `seats`, `total_kopecks` | число и сумма **активных** строк; 0 допустим только у `FULL_TERMINATION` (ограничения 0017/0021 `seats ≥ 1`, `total > 0` заменяются условными) |
| `legal_release_*`, `pd_consent_*`, `contract_snapshot_sha256` | принятые в согласии; у `STAFF_RECORDED` — копия предыдущей ревизии |
| `accepted_at` / `effective_at` | время согласия / время вступления (БД) |
| `deposit_until`, `balance_due_at` | **замороженные сроки ревизии** (§5.6) |
| `predecessor_hash`, `revision_hash` | как в 0017/0021; в хэш добавляются `amendmentRef`, `candidateHash`, сроки. Хэши прежних ревизий пересчитываются без изменений (те же ключи JSON) |

Строки ревизии: по одной на **каждое** место покупки. `line_status` — одно из трёх значений, и БД выводит его из
состояния места при вступлении, а не принимает от вызывающего:

| `line_status` | Состояние места | Смысл |
|---|---|---|
| `ACTIVE` | `CONFIRMED` (у неоплаченной покупки, только `TERMS_REACCEPTANCE`, — `HELD`/`RELEASED`) | действующее место договора: входит в `seats`, `total_kopecks`, долг, перенос, правила допуска |
| `CANCELLED` | `CANCELLED` | отменено поправкой; цена — последняя договорная, только для истории |
| `SETTLED` | `REFUND_SETTLED` | «оплата без места», урегулированная возвратом (0021/0022/0026); цена — справочно |

**Активная строка** — только `ACTIVE`. `CANCELLED` и `SETTLED` переносятся в каждую следующую ревизию без изменений
(тип, цена, основа цены, статус). Они не входят в `seats`, `total_kopecks`, `due`, `excess`, не переносятся на другой
выезд и не занимают там место, не участвуют в правилах допуска и не меняются никаким основанием. В кандидате и хэше
они присутствуют со своим статусом. `lines_sha256` включает `line_status`. Строки ревизий до 0027 колонки не имеют:
для них статус читается из состояния места по той же таблице.

Покупка с местом `PAID_NO_SEAT_EXCEPTION` поправкам недоступна до урегулирования этого места (§3.1). Правило цены строки зависит от основания
(§4, столбец «Цена»); проверяет триггер строки, а не вызывающий.

### 2.4. Отказы, которые меняют состояние, сохраняются

SQL-исключение откатывает весь вызов функции (урок `NOTHING_DUE` в #91). Поэтому:

- команда, которая при отказе **должна что-то записать** (закрыть поправку `STALE` или `EXPIRED`, израсходовать ссылку
  согласия), возвращает результат **значением**, а не исключением. `fn_amendment_consent` возвращает
  `(result, amendmentRef, consentRef, revision)`, где `result` ∈ `COMMITTED`, `CONSENTED`, `REPLAYED`, `STALE`,
  `EXPIRED`, `NOT_OPEN`. Закрытие фиксируется вместе с вызовом;
- команда, которая при отказе **ничего не меняет**, отказывает исключением, как в 0021–0026;
- срок истекает и без запроса: `maintain` вызывает `fn_amendments_close_due()` отдельным оператором (как
  `fn_seat_holds_close_lapsed`). Поправку с операцией в полёте она не закрывает;
- TS переводит `STALE` / `EXPIRED` / `NOT_OPEN` в объяснение для покупателя, а не в код ошибки.

Тест: согласие с устаревшим хэшем → результат `STALE`; **другое соединение** после возврата видит `state = CLOSED`,
`closed_reason = STALE`; ревизия не создана; повтор → `NOT_OPEN`. То же для `EXPIRED`.

## 3. Матрица состояний поправки

```
            согласие (без оплаты) / запись сотрудника ─────────────────────────────► COMMITTED
  OPEN ──┬─ согласие + операция AMENDMENT ── SUCCEEDED, вступление возможно ──────► COMMITTED
         │                                 └ SUCCEEDED, вступление невозможно ─► NEEDS_RESOLUTION ─(заявка решена)─► CLOSED(SETTLED)
         ├─ отзыв сотрудником / отказ покупателя / срок / устарела / вытеснена ─────► CLOSED(<причина>)
         └─ операция FAILED ───────────────────────────────────────────────────────► CLOSED(PAYMENT_FAILED)
```

Отдельных состояний `CONSENTED` / `PAYMENT_PENDING` нет: согласие — факт (`purchase_amendment_consent`), платёж — статус
своей `bank_operation` (02 §9.2).

| Событие ↓ / состояние → | `OPEN`, согласия нет | `OPEN`, согласие есть, операции нет | `OPEN`, операция `AMENDMENT` в полёте (`INTENDED`/`REGISTERED`/`UNKNOWN` или `application_due`) | `NEEDS_RESOLUTION` | `COMMITTED` / `CLOSED` |
|---|---|---|---|---|---|
| Согласие с актуальным хэшем | вступление (если оплата не нужна) или запись согласия | повтор: тот же `consentRef` | повтор: тот же `consentRef` | `AMENDMENT_NOT_OPEN` | повтор того же согласия возвращает итог; иначе `AMENDMENT_NOT_OPEN` |
| Согласие с другим хэшем / база изменилась | результат `STALE` значением, `CLOSED(STALE)` сохраняется (§2.4) | невозможно: база заморожена (I-12) | невозможно | `AMENDMENT_NOT_OPEN` | `AMENDMENT_NOT_OPEN` |
| Отказ покупателя | `CLOSED(REJECTED)` | `CLOSED(REJECTED)` | `AMENDMENT_PAYMENT_IN_FLIGHT` | — | `AMENDMENT_NOT_OPEN` |
| Отзыв сотрудником (`amendment.record`, причина) | `CLOSED(WITHDRAWN)` | `CLOSED(WITHDRAWN)` | `AMENDMENT_PAYMENT_IN_FLIGHT` | — | `AMENDMENT_NOT_OPEN` |
| Срок истёк (`maintain`, часы БД) | `CLOSED(EXPIRED)` | `CLOSED(EXPIRED)` | **не закрывается**: ждёт исхода банка, срок не снимает UNKNOWN | — | — |
| Открыть операцию `AMENDMENT` | `AMENDMENT_CONSENT_REQUIRED` | одна операция; повтор возвращает её | повтор возвращает её | `AMENDMENT_NOT_OPEN` | `AMENDMENT_NOT_OPEN` |
| Операция `SUCCEEDED`, вступление возможно | — | — | `COMMITTED`, деньги распределены по кандидату | — | поздний успех после `CLOSED` → заявка `AMENDMENT_LATE_PAYMENT` |
| Операция `SUCCEEDED`, вступление невозможно (нет места, T−24 цели, база изменилась) | — | — | `NEEDS_RESOLUTION` + заявка `AMENDMENT_UNCOMMITTABLE`; деньги не гасят старый долг | — | — |
| Операция `FAILED` | — | — | `CLOSED(PAYMENT_FAILED)`; новый платёж — только новая поправка | — | — |
| Заявка урегулирования решена (возврат или решение OWNER) | — | — | — | `CLOSED(SETTLED)` | — |
| Вступила другая ревизия той же покупки | `CLOSED(STALE)` | невозможно (§6, I-12) | невозможно | — | — |
| TOUR-89: новая редакция C при открытом обязательстве к B | `CLOSED(SUPERSEDED)` + новое обязательство к C | то же | то же | — | — |
| Перенос или прекращение вступили при открытом обязательстве TOUR-89 | `CLOSED(RESOLVED_BY_OTHER)`, исход записывается (§9) | то же | — | — | — |

`closed_reason`: `REJECTED`, `WITHDRAWN`, `EXPIRED`, `STALE`, `SUPERSEDED`, `RESOLVED_BY_OTHER`, `PAYMENT_FAILED`,
`SETTLED`. На покупку одновременно открыто не больше **одной** поправки сотрудника и не больше **одного** обязательства
TOUR-89 (частичные уникальные индексы).

### 3.1. Состояния места: что добавляет A2b-3

К матрице §3 контракта трека A добавляется только переход `CONFIRMED → CANCELLED`. Триггер `seat_slot` разрешает его,
только если в этой же транзакции вставлена ревизия с основанием `PARTIAL_CANCELLATION` или `FULL_TERMINATION` и
строка этого места в ней `CANCELLED`. Обратного перехода нет. `DEPARTURE_TRANSFER` места не отменяет: при целом переносе
(OWNER Q4) все активные места остаются `CONFIRMED`, меняется выезд ревизии; ранее отменённые строки переносятся
`CANCELLED` и на цели место не занимают.

| Состояние места | Можно ли менять поправкой |
|---|---|
| `CONFIRMED` | да, всеми основаниями A2b-3 |
| `HELD`, `RELEASED` (неоплаченная покупка) | только `TERMS_REACCEPTANCE` (A2b-10). Основания A2b-3 — `AMENDMENT_PURCHASE_NOT_CONFIRMED` |
| `PAID_NO_SEAT_EXCEPTION` | нет: сначала назначение места или возврат (TOUR-27) — `AMENDMENT_SEAT_NOT_ELIGIBLE` |
| `REFUND_SETTLED`, `CANCELLED` | конечные; строка переносится в следующую ревизию без изменений со статусом `SETTLED` / `CANCELLED`, не активна (§2.3) |

### 3.2. Состояние покупки × основание

Состояние покупки выводится, а не хранится.

| Основание ↓ / состояние покупки → | Не оплачена, места `HELD`/`RELEASED` | Подтверждена, долг или оплачена полностью | Операция в полёте или `application_due` | Открыта заявка урегулирования (кроме `PAID_NO_SEAT`) | Открыто обязательство TOUR-89 без согласия | Все места отменены | Закрыта по 8B |
|---|---|---|---|---|---|---|---|
| `TICKET_TYPE_CORRECTION` | `AMENDMENT_PURCHASE_NOT_CONFIRMED` | ✔ | `AMENDMENT_PAYMENT_IN_FLIGHT` | `AMENDMENT_SETTLEMENT_PENDING` | `DEPARTURE_CHANGE_UNRESOLVED` | `AMENDMENT_PURCHASE_TERMINATED` | `PURCHASE_CLOSED` |
| `PARTICIPANT_REPLACEMENT` | то же | ✔ | то же | ✔ (деньги не затрагивает) | `DEPARTURE_CHANGE_UNRESOLVED` | то же | то же |

## 5. Деньги: интеграция с реестром 0026

### 5.1. Доли: деньги места с происхождением

Деньги места учитываются не одной суммой, а **долями** — по исходному взысканию (`COLLECTION`, `SUCCEEDED`). Доля
`(место, взыскание X)` равна:

```
holding(место, X) = Σ seat_money_allocation(X → место)
                  + Σ seat_money_transfer(X, → место) − Σ seat_money_transfer(X, место →)
                  − Σ подтверждённых bank_refund_allocation(место, возврат R), где R.refunds_operation_id = X
```

| Величина | Определение |
|---|---|
| `price` | цена строки текущей ревизии; у `CANCELLED` — последняя договорная, только справочно |
| `net(место)` | Σ по X `holding(место, X)` |
| `reserved(место, X)` | доля, отданная открытой заявке и ещё не исполненная (§5.5) |
| `available(место, X)` | `holding − reserved` |
| `due` | у активной строки `max(0, price − net)`; у `CANCELLED` — 0 |
| `excess` | у активной строки `max(0, net − price)`; у `CANCELLED` — `net` |

**Порядок долей — принятый технический порядок расходования, а не банковская хронология.** Когда деньги места нужно
взять (для переноса §5.3 или заявки §5.5), доли берутся по **времени намерения оплаты** их взыскания, от позднего к
раннему: `bank_operation.created_at`, который ставит БД при открытии операции до регистрации в банке. При равенстве — по
`bank_operation_ref`. Порядок детерминирован и не зависит от того, в каком порядке пришли callback и read-back.

`outcome_at` для порядка не используется: 0022 ставит его временем обработки свидетельства (`clock_timestamp()`), и
поздний callback сделал бы старый платёж «новее». Времени оплаты от банка (`providerPaidAt`) в схеме нет. Контракт
**не утверждает**, что порядок намерений всегда совпадает с фактической хронологией оплат. В штатном потоке они
совпадают: у одной покупки новое взыскание не открывается, пока прежнее в полёте или не применено (`seat_hold_open`,
`bank_operation_balance_in_flight`, I-11, I-12). Но противоречивый исход банка (`FAILED → SUCCEEDED`, v1.9.1 §2 п.4)
даёт поздно признанный успех старого намерения. Такие деньги обычно уходят в заявку (`NEWER_CYCLE_EXISTS`,
`UNALLOCATED_MONEY`), а не на места. Корректность возврата держится не на порядке, а на лимитах ниже: возврат всегда
идёт через исходное взыскание доли и не превышает её остатка.

Порядок фиксирован, вручную не меняется. Если банк отказывает в возврате через исходное взыскание, доля остаётся
открытой, заявка ждёт оператора. Перевести возврат на другое взыскание нельзя (OWNER Q3: возврат — через исходное
взыскание).

**Лимиты возврата — три уровня, все проверяет БД:**

1. по взысканию: Σ неотказанных возвратов `X` ≤ сумма `X` (0022, без изменений);
2. по доле: подтверждённый возврат из `X`, отнесённый на место, ≤ `holding(место, X)`;
3. по заявке: возвраты, открытые по доле заявки (включая операции в полёте), ≤ остатку этой доли.

Изменения 0022/0026 в 0027:
- представления `seat_money` / `purchase_money` считают `net`/`due` по долям, итог — только по активным строкам (§2.3). 0026 вычитала из цены валовое
  `paid` без возвратов: это было верно, пока возвраты шли только по «оплате без места»;
- `fn_seat_money_allocation_guard` сравнивает с ценой `net + amount`, в отменённое место не распределяет;
- в `bank_refund_allocation` снимаются `UNIQUE (seat_slot_id)` и `UNIQUE (settlement_case_id)`: одно место и одна
  заявка могут получить несколько частичных возвратов. Добавляется `settlement_case_lot_id`. Охрана — лимиты 2 и 3.
  Идемпотентность `fn_seat_slot_refund_settled` держится переходом `PAID_NO_SEAT_EXCEPTION → REFUND_SETTLED`, а не
  UNIQUE: её регрессионные тесты 0022/0026 сохраняются.

### 5.2. Денежный снимок кандидата

На каждое место в хэш кандидата входят `price` до и после, `net`, `due` и `excess` после вступления, а также
перераспределения §5.3. Любое новое распределение, возврат или операция по покупке меняют снимок: несогласованная
поправка устаревает (результат `STALE`, §2.4). Так «новый сторонний платёж делает предложение устаревшим» (02 §9.2).
Согласованная поправка снимок не теряет: после согласия новые обычные платежи запрещены (§5.7).

### 5.3. Перераспределение внутри покупки

При вступлении `excess` **активных** мест переносится на `due` других активных мест той же покупки. Порядок
детерминирован:
- места-источники — по возрастанию `position`, доли внутри источника — по порядку §5.1;
- получатели — по возрастанию `position`.

Запись `seat_money_transfer` содержит поправку, **исходное взыскание `X`**, место-источник, место-получатель и сумму.
Охрана: сумма ≤ `available(источник, X)`; `net(получатель) + сумма ≤ price(получатель)`; оба места одной покупки.
Записи только добавляются.

Так покрываются правила 02 §9.3: переплата одного места гасит долг другого, а более дешёвая поездка сокращает остаток
без возврата. Происхождение не теряется. Пример ревью:
- место A получило депозит взысканием `X1` и остаток взысканием `X2`; цена A снизилась на 5 000 ₽;
- перенос 5 000 ₽ на место B записан как доля `(место B, X2)`;
- затем место B отменено, и эти 5 000 ₽ возвращаются **из взыскания `X2`** в пределах его остатка (лимиты 1–2).

**Деньги отменённого места никогда не зачитываются** (OWNER Q3): ни автоматически, ни командой сотрудника, ни решением
OWNER. Охрана `seat_money_transfer` отклоняет источник, чья строка в текущей ревизии `CANCELLED`
(`SEAT_MONEY_SOURCE_CANCELLED`), для любого логина. Колонки `case_id` у переноса нет: исполняемого пути зачёта в DDL не
существует. Деньги отменённого места уходят только в заявку `CANCELLATION_SETTLEMENT` (§5.5). Перенос между
**активными** местами одной покупки, описанный выше, сохраняется. Между покупками деньги не переносятся никогда.

### 5.4. Оплата до вступления (`purpose = AMENDMENT`)

- Новое значение `bank_operation.purpose`. Операция ссылается на `amendment_id`, а не на цикл; сумма равна
  `requires_payment_kopecks`. Открыть её можно только после согласия и до `expires_at` с техническим запасом на
  регистрацию в банке (MK-POLICY §2 п.6). На поправку — одна операция; повтор возвращает её.
- При `SUCCEEDED` применение (`fn_bank_operation_apply_locked`) вызывает вступление. Деньги распределяются **по
  кандидату** (на `due` после вступления) в той же транзакции, что ревизия. Если вступление невозможно — `NEEDS_RESOLUTION`
  и заявка `AMENDMENT_UNCOMMITTABLE`. Деньги остаются фактом операции и **не гасят старый долг** (02 §9.2, TRANSFER-PAY-03).
- При `FAILED` — `CLOSED(PAYMENT_FAILED)`. Места и деньги не меняются.

**Схема операции `AMENDMENT` (0028).** Ограничения 0026 рассчитаны на две формы взыскания: на цикле (`FULL`/`DEPOSIT`)
и без цикла (`BALANCE`). `bank_operation_cycle` требует `seat_hold_id` у любого взыскания, кроме `BALANCE`, поэтому
операция `AMENDMENT` без цикла сейчас была бы отклонена. 0028:
- заменяет `bank_operation_cycle` на NULL-безопасное ограничение. У операций до 0026 `purpose` равен NULL и читается как
  `FULL`, поэтому `NOT IN` нельзя: `NULL NOT IN (...)` даёт NULL, а `CHECK` пропускает NULL.
  ```sql
  CHECK ((kind = 'COLLECTION' AND purpose IS DISTINCT FROM 'BALANCE' AND purpose IS DISTINCT FROM 'AMENDMENT')
         = (seat_hold_id IS NOT NULL))
  ```
- добавляет `bank_operation.amendment_id` с `CHECK ((purpose IS NOT DISTINCT FROM 'AMENDMENT') = (amendment_id IS NOT NULL))`
  и `UNIQUE (amendment_id)`: одна операция на поправку за всё время. Правило для новых ограничений 0027/0028: каждое
  сравнение с колонкой, допускающей NULL, — через `IS [NOT] DISTINCT FROM`. После `FAILED` поправка закрывается, новый платёж —
  только новой поправкой;
- делает `amendment_id` неизменяемым, как `purpose` (триггер 0026 `fn_bank_operation_purpose_immutable` расширяется);
- открывает операцию функцией `fn_amendment_payment_open(amendmentRef, sessionToken, provider, account)` под порядком
  §7.2 (выезды поправки → документ-заказ → поправка): сессия покупателя (0023), согласие записано, поправка `OPEN`, до
  `expires_at` остаётся банковское окно с запасом. Повтор возвращает ту же операцию, другой провайдер —
  `AMENDMENT_PAYMENT_IN_FLIGHT`. Регистрация в банке, свидетельства и read-back — как у прочих взысканий (TOUR-77): по
  `bankOperationRef`;
- `fn_purchase_payment_blocker` (§5.7) и `bank_operation_balance_in_flight` к операции `AMENDMENT` не применяются;
  обычные платежи при согласованной поправке блокирует I-12.

Тесты: прямой DML `AMENDMENT` без `amendment_id`, с `seat_hold_id` или второй операции на ту же поправку отклоняется для
любого логина; взыскание с `purpose = NULL` без `seat_hold_id` и взыскание с `purpose = NULL` и `amendment_id`
отклоняются; два конкурентных открытия на одну поправку — одна операция (второе соединение держит реальную
блокировку, оба порядка); открытие без согласия, после срока или после `FAILED` — отказ.

### 5.5. Заявки урегулирования по поправкам (TOUR-27)

Заявка 0022 — это заявка на **одну** банковскую операцию: `bank_operation_id NOT NULL`, `UNIQUE (bank_operation_id,
reason)`, а `fn_bank_settlement_resolve` для `REFUNDED` требует возврат всей суммы этой операции. Для причин 0022/0026
(`PURCHASE_CLOSED_LATE_PAYMENT`, `NEWER_CYCLE_EXISTS`, `PAID_NO_SEAT`, `EVIDENCE_MISMATCH`, `CONTRADICTORY_EVIDENCE`,
`UNALLOCATED_MONEY`) эта модель и функция **не меняются**. Для поправок 0027 вводит заявки **по долям**.

**Причины и доли.** Состав долей фиксируется при открытии заявки:

| Причина | Когда открывается | Доли (`settlement_case_lot`) | `amount_kopecks` |
|---|---|---|---|
| `AMENDMENT_OVERPAYMENT` | после §5.3 у активных мест остался `excess` | по каждому такому месту — его доли на сумму `excess`, по порядку §5.1 | Σ `excess` |
| `CANCELLATION_SETTLEMENT` | частичная отмена или прекращение, `net > 0` у отменённых мест | все доли отменённых мест | Σ `net` отменённых мест |
| `AMENDMENT_UNCOMMITTABLE` | оплата `AMENDMENT` успешна, вступление невозможно | одна доля «вне мест» этого взыскания | сумма операции |
| `AMENDMENT_LATE_PAYMENT` | успех `AMENDMENT` после закрытия поправки | то же | сумма операции |

Изменения таблиц:
- `bank_settlement_case`: `bank_operation_id` допускает NULL только у причин поправок; добавляются `amendment_id` и
  `amount_kopecks`; `UNIQUE (amendment_id, reason)`.
- `bank_operation`: `settlement_case_id` у `REFUND`; `CHECK (kind = 'COLLECTION' OR application_due IS NULL)` 0022
  ослабляется до «или возврат по заявке» — только для распределения подтверждённого возврата по долям.
- `bank_settlement_case.retention_allowed` — вычисляется при открытии (§5.5, `RETAINED`), неизменяем.
- новая причина 0022-модели `REFUND_CONTRADICTED` — на противоречивый исход возврата (ниже).
- `settlement_case_lot (case, место | NULL, исходное взыскание X, amount)`. Доля резервирует деньги: пока заявка открыта,
  `reserved` не переносится §5.3 и не идёт в другую заявку.

**Исходы доли** — два, оба append-only:
- `REFUNDED`. OWNER (`refund.execute`) открывает возврат по доле: `fn_settlement_refund_open(case, X, amount)`,
  сумма ≤ остатка доли за вычетом возвратов в полёте. «В полёте» здесь — `INTENDED`/`REGISTERED`/`UNKNOWN` **и `SUCCEEDED` с `application_due`**: подтверждённый, но ещё не распределённый возврат держит резерв до `maintain`, второй возврат той же суммы не открывается. Возврат — `bank_operation` `REFUND` с `refunds_operation_id = X`
  и `settlement_case_id`. Подтверждённый возврат распределяется на доли заявки (`bank_refund_allocation` с
  `settlement_case_lot_id`) путём применения исхода — тем же, что у взысканий (§7.2):
  - `fn_bank_operation_record` при `SUCCEEDED` возврата по заявке ставит `application_due = SUCCEEDED` — в 0022 он
    ставится только взысканиям;
  - `fn_bank_operation_apply_locked` распределяет возврат на доли заявки с источником `X` по возрастанию `id` доли и
    закрывает заявку, если все доли исполнены. Подтверждение банка и попытка распределения — одна транзакция; сбой
    распределения внутри неё (подтранзакция, как в 0022) оставляет банковский факт и `application_due`, и
    `fn_bank_operations_apply_due` (`maintain`) повторяет. Повторное применение ничего не распределяет второй раз
    (`UNIQUE (bank_operation_id, outcome)` в `bank_operation_application`).

  `UNKNOWN` резерв держит, второй возврат на ту же сумму не открывается. Неудачный (`FAILED`) возврат освобождает
  резерв, **только если отказ подтверждён авторитетным read-back** (свидетельство `READ_BACK` с `FAILED`). Отказ только
  по ответу регистрации или callback резерв держит, пока read-back его не подтвердит: это снижает риск противоречия
  ниже. На одну заявку — несколько возвратов, в том числе из разных взысканий.

**Противоречивый исход возврата** (`FAILED → SUCCEEDED`, 0022 допускает его и для возвратов: `contradicted_at`).
Предотвратить его полностью нельзя: банк может признать успех и после read-back. Сценарий: доля 10 000 ₽ → возврат R1
`FAILED` → резерв освобождён → открыт R2 на 10 000 ₽ → банк признаёт успех R1.
- **Банковский факт сохраняется всегда**: статус `SUCCEEDED`, `contradicted_at`, свидетельство (0022).
- **Применение противоречивого возврата ничего не распределяет автоматически.** Вместо распределения оно открывает
  заявку `REFUND_CONTRADICTED` на R1: по операции, модель 0022, новая причина.
- **Заявка поправки, к которой относится R1, замораживается**, пока `REFUND_CONTRADICTED` открыта: по ней не открываются
  новые возвраты, не записываются удержания, она не закрывается. Деньги затронутого взыскания `X` ни на что не
  расходуются: перенос §5.3, новые доли и новые заявки по `X` отклоняются (`REFUND_CONTRADICTION_PENDING`). Покупка
  блокирует новые поправки и платежи как при открытой заявке (§3.2, §5.7).
- Оператор видит конфликт в `bank_settlement_open`: R1, другие возвраты по доле, их статусы, записанные исходы доли
  (возвраты и удержания). Пока любой другой возврат по той же доле в полёте, с `application_due` или `FAILED` без
  read-back, урегулирование **ждёт**: новых возвратов нет. Отменить такой возврат в банке, если это возможно, — вне
  системы, с записью.
- **Урегулирование учитывает все уже записанные исходы доли — и возвраты, и удержания.** К моменту признания R1 доля
  могла быть не исполнена, исполнена другим возвратом R2, исполнена удержанием `RETAINED` (исходная заявка тогда уже
  закрыта) или исполнена смешанно. OWNER (`refund.execute`) вызывает `fn_refund_contradiction_resolve(case, reason,
  decision)`. Функция **детерминированно** раскладывает сумму R1 по трём частям, по порядку:
  1. **`to_lot`** — неисполненный остаток доли: R1 распределяется на долю (`bank_refund_allocation` с
     `settlement_case_lot_id`);
  2. **`retention_reversed`** — удержанная часть доли: банк фактически вернул эти деньги, поэтому удержание
     корректируется записью `settlement_lot_retention_reversal` (удержание, сумма, R1, заявка `REFUND_CONTRADICTED`,
     OWNER, причина). Исходная запись удержания не меняется и не удаляется. R1 распределяется на долю на эту сумму.
     Удержания разворачиваются от позднего к раннему, частично — если нужно;
  3. **`over_refund`** — остаток R1 сверх доли (её возвратов и удержаний): относится к `over_refund(X)` вне мест с этой
     заявкой. Нужно решение OWNER с причиной: требование к покупателю или списание. Повторного списания с покупателя
     нет.

  Части записываются в `contradiction_outcome (to_lot, retention_reversed, over_refund, decision)` и в сумме равны
  R1. Исходная заявка поправки, если она уже закрыта, **не переоткрывается** (`resolved_*` неизменяемы).
  Корректировки видны в представлении `settlement_case_corrections`, а исполнение доли после корректировки остаётся
  полным: подтверждённые возвраты + (удержания − развороты) = сумма доли.
- **Закрыть `REFUND_CONTRADICTED` можно только `fn_refund_contradiction_resolve`.** Общая `fn_bank_settlement_resolve`
  отказывает `REFUND_CONTRADICTED_REQUIRES_SPECIAL_RESOLUTION` в обеих ветках, `REFUNDED` и `OWNER_DECISION`. Охрана
  строки `bank_settlement_case` проверяет **данные**, а не вызывающую функцию, поэтому прямой `UPDATE` её тоже не
  обходит. `resolved_at` у `REFUND_CONTRADICTED` ставится, только если:
  - нет другого возврата по доле в полёте, с `application_due` или `FAILED` без read-back;
  - записан `contradiction_outcome`, и `to_lot + retention_reversed + over_refund = сумма R1`;
  - `to_lot` ≤ неисполненного остатка доли, `retention_reversed` ≤ действующих удержаний доли, `over_refund` ≥ 0, и
    если `over_refund > 0`, то записано решение OWNER;
  - распределения и развороты R1 записаны ровно на эти суммы.

  Для любой истории доли — не исполнена, исполнена возвратом, удержанием или смешанно — ровно одна раскладка
  выполнима, поэтому бессрочной блокировки нет. Пока другой возврат в полёте, условие не выполнено: заявку не закрыть
  никаким путём.
- После закрытия `REFUND_CONTRADICTED` заморозка снимается.
- `RETAINED`. `settlement_lot_retention`: только OWNER (`refund.execute`), причина, правовое основание и ссылка на
  доказательство допустимых фактических расходов (без ПД); автоматической формулы удержания нет. Допустимо **только** в
  `CANCELLATION_SETTLEMENT` при добровольном отказе покупателя (флаг заявки `retention_allowed`, вычисляется при
  открытии). В заявках `AMENDMENT_OVERPAYMENT`, `AMENDMENT_UNCOMMITTABLE`, `AMENDMENT_LATE_PAYMENT`, при прекращении по
  инициативе организатора и при отказе от существенного изменения TOUR-89 удержание отклоняется
  (`RETENTION_NOT_ALLOWED`). Страховая премия автоматически не удерживается (v1.8.2 §2.5).

Зачёта (`OFFSET`) нет (OWNER Q3). Исполненная доля — подтверждённо возвращённая или удержанная — повторно не
резервируется, не переносится и в другую заявку не попадает.

**Закрытие заявки.** Заявка закрывается **автоматически** командой, которая записала последний исход, когда для каждой
доли выполнено: распределённые подтверждённые возвраты + удержано = `amount` доли, и ни одного возврата по заявке нет в
полёте или с `application_due`. Итог: `resolution = REFUNDED`, если всё возвращено, иначе `OWNER_DECISION` с причинами
удержаний;
`resolved_by` — автор последнего исхода. Ручного «закрыть заявку» без исходов нет. `refund_operation_id` для заявок по
долям — NULL; `CHECK` 0022 становится условным по причине.

Пример ревью: за место заплачено 20 000 ₽ двумя взысканиями `D` 5 000 и `B` 15 000. Цена снижена до 10 000 ₽,
`excess` = 10 000. Доля заявки — `(место, B, 10 000)`. Возврат из `B` на 10 000 ₽ подтверждён → доля исполнена →
заявка `REFUNDED`. Если банк вернул 6 000 и 4 000 двумя операциями — та же заявка, два распределения.

**Доли и сверка.** I-10 различает **назначение** денег (куда поступление направлено, накопительно и навсегда) и
**текущий остаток** (сколько денег взыскания у нас сейчас). Промежуточные состояния учитываются явно. Представление
`bank_money_pending` показывает подтверждённое, но не применённое: взыскания и возвраты с `application_due`, а также
подтверждённые возвраты 0022, ещё не отнесённые их функцией урегулирования. `maintain` применяет его отдельным
оператором (`fn_bank_operations_apply_due`).

Открытая заявка по покупке блокирует новые `BALANCE` (0026, `BALANCE_SETTLEMENT_PENDING`) и новые поправки (§3.2).

### 5.6. Сроки долга замораживаются в ревизии

0026 вычисляет `deposit_until` / `balance_due_at` по **живому** выезду. После TOUR-89 правка расписания сдвигала бы старый
долг, а v1.8.2 §7.1 это запрещает. A2b-3 записывает оба срока в ревизию:
- `INITIAL` — от выезда на момент создания;
- поправка — копия предыдущей ревизии;
- новые сроки — только по согласию в кандидате (перенос, `DEPARTURE_CHANGE_ACCEPTANCE`);
- продление долга менеджером — отдельное событие MK-C01, без ревизии (вне A2b-3).

Окно оплаты остатка в `fn_bank_operation_open_payment` проверяется по сроку текущей ревизии. Для **новых допусков**
(цикл, депозит, перенос) при неурегулированном изменении расписания действует защитная граница `min(старое, новое)`
(v1.8.2 §7.1). У ревизий, созданных до этой миграции (только синтетика), сроков нет: они вычисляются как в 0026.

Пример ревью: X = 10 000 без места → `assigned_out` = 10 000; возврат 10 000 подтверждён и распределён → `out_balance` = 0, остаток 0; до распределения `r_pending` = 10 000, и (В) сходится | сверочный запрос по каждому X; тест-инвариант после **каждого** шага: до подтверждения банка, после подтверждения и до применения (сбой распределения, как в #91), после `maintain`, после подтверждения возврата и до распределения, после распределения, полный возврат денег вне мест |

## 7. Блокировки и конкуренция

### 7.1. Как сейчас (0013–0026, проверено по SQL)

| Шаг | Как берётся | Кто |
|---|---|---|
| Выезд | `fn_lock_checkout_departure(slug)`: строка `departure` `FOR SHARE`, затем `pg_advisory_xact_lock('departure:'‖slug)`. Редакционные записи и управление выездом: строка (UPDATE / `FOR NO KEY UPDATE`), затем тот же advisory. Пакетные: advisory `departure-status-batch`, затем выезды по возрастанию `id` | checkout, `fn_purchase_lock_departure`, публикация, пауза, пакеты 0019 |
| Документ-заказ | `orders` `FOR UPDATE` — **точка сериализации покупки** | rehold, закрытие 8B, 0025/0026 open, `fn_bank_operation_lock` |
| После документа-заказа | 0025/0026 open: цикл, затем операции. 0022 apply (`fn_bank_operation_lock` → `fn_bank_operation_apply_locked`): операция, затем цикл и места | под одной блокировкой документа-заказа разный порядок цикла и операции взаимной блокировки не даёт |
| Без документа-заказа | `fn_bank_refund_open` (строка взыскания), `fn_bank_refund_allocate` (строка возврата) — по одной строке. `fn_seat_holds_close_lapsed`, `fn_priced_document_orders_close` — `SKIP LOCKED` | цикла ожидания не образуют |

Контракт **не утверждает**, что существует единый строгий порядок всех строк. Он утверждает правило, которому следуют все
пути, и называет функции, которые 0027/0028 меняют.

### 7.2. Правило для 0027/0028

- **R1. Выезды.** Каждый путь, который меняет места, реестр, заявки или поправки покупки, сначала берёт выезды
  **так же, как checkout**: строка `FOR SHARE` + advisory по slug. Два выезда (перенос) — по возрастанию `departure.id`,
  как пакеты 0019.
- **R2. Документ-заказ.** Затем — строка документа-заказа покупки. Все команды поправок и заявок по долям
  сериализуются на ней с платежами, применением исходов банка, rehold и закрытием 8B.
- **R3. После документа-заказа** — строка поправки, затем строки в любом порядке. Взаимной блокировки нет, потому что
  каждый, кто берёт больше одной строки покупки, уже держит документ-заказ (R2).
- **R4. Одна строка без документа-заказа** допустима только для `fn_bank_refund_allocate` (0022): она меняет одну строку
  уже подтверждённого возврата. **Открытие любого возврата идёт по R1–R2**, иначе оно гоняется с созданием заявки по
  долям. Поэтому 0027 заменяет `fn_bank_refund_open` (та же сигнатура): выезд → документ-заказ → строка взыскания. Новый
  `fn_settlement_refund_open` идёт так же.
- **R5. Взыскания доли.** Создание заявки по долям (вступление отмены или прекращения, переплата, `NEEDS_RESOLUTION`) и
  открытие возврата по доле после документа-заказа блокируют **каждое** затронутое взыскание `X` `FOR UPDATE` по
  возрастанию `bank_operation.id`. После блокировок заново читаются все возвраты по `X`: в полёте, подтверждённые и не
  распределённые. Если есть возврат по `X`, не отнесённый ни к доле, ни к заявке 0022, резерв не создаётся.
  Вступление поправки отклоняется (`AMENDMENT_PAYMENT_IN_FLIGHT`, I-11) до урегулирования этого возврата.

### 7.3. Смешанные сценарии

| Сценарий | Почему безопасно | Результат |
|---|---|---|
| Два переноса на последнее место цели | оба берут выезды по `id`; второй ждёт первый на выезде с меньшим `id` | первый вступает; второй при вступлении — `NOT_ENOUGH_SEATS`, его исходные места не освобождены |

## 9. TOUR-89/92: изменение проданного выезда

1. Публикация изменённой версии выезда с договорными полями (TOUR-92) создаёт по каждой затронутой покупке
   обязательство — поправку `DEPARTURE_CHANGE_ACCEPTANCE` с режимом:
   - `CONSENT` — `BUYER_HASH` по `appendixHash`;
   - `INFORM` — `INFORMED`, только при правовом основании TOUR-84.

   Каждая покупка группы — отдельно (v1.9.0 §8).
2. Базовая редакция покупки — выезд и версия её текущей ревизии. Новая редакция C при открытом обязательстве к B
   закрывает его `SUPERSEDED` и открывает обязательство к C. Ссылки на B устаревают, операторские задачи по B
   остаются (v1.8.2 §7 п.4, п.10).
3. Пока обязательство `CONSENT` открыто, действуют I-13 и §5.7: новые платежи по покупке запрещены. Уже
   зарегистрированная операция завершается на условиях своей регистрации (v1.9.1 §4 п.2).
4. 72 часа — срок внимания оператора, а не акцепт. Обязательство без согласия по сроку **не закрывается**: у него нет
   `expires_at`.
5. Исходы для покупателя:
   - согласие → ревизия `DEPARTURE_CHANGE_ACCEPTANCE`;
   - перенос → `DEPARTURE_TRANSFER`, обязательство закрывается `RESOLVED_BY_OTHER`, исход `TRANSFERRED`;
   - полный возврат → `FULL_TERMINATION` с причиной `ORGANIZER_CHANGE`, исход `REFUNDED`.

   Исход договора (`contractDisposition`) и операторская задача — независимые оси (v1.8.2 §7 п.8). Задача — TOUR-92/102,
   не A2b-3.
6. Покупка с операцией в полёте: согласие записывается, вступление ждёт исхода операции (I-11).
