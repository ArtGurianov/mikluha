# TOUR-35 · Профиль персональных данных native-продаж: платежи, фискализация, ЕИС, депозиты

- **Статус:** PROPOSED data map для юридической проверки. Не является юридическим заключением,
  подписанным поручением, изменением опубликованных документов или разрешением live-обработки.
- **Задача:** [TOUR-35](https://app.plane.so/art-workspace/browse/TOUR-35/) (ART-273): расширить
  карту ПД на native платёжных/фискальных контрагентов, депозиты, ревизии покупки и хранение;
  Refref не получает досье туристов. Вход для [TOUR-84](https://app.plane.so/art-workspace/browse/TOUR-84/)
  (оферта §13), TOUR-80 (ЕИС), TOUR-79 (операторский доступ), TOUR-45 (сроки хранения заказов).
- **Источники:** [MK-POLICY v2.4 §7](../refref-v10/06-mk-policy-v2.4.md), [04 §7](../refref-v10/04-fiscal-eis-and-legal-impact.md#7-персональные-данные-и-хранение),
  действующие `content/legal/soglasie-pd.yml` (v1.0), `privacy-policy.yml`, `oferta.yml` §13–14,
  схема Commerce 0001–0019.

## 1. Субъекты и категории

| Субъект | Данные | Где в системе |
| --- | --- | --- |
| Заказчик (турист № 1) | ФИО, дата рождения, гражданство, вид/серия/номер документа, телефон, email | `order_contact`, `order_passenger`, `purchase_revision_participant` |
| Другие туристы (взрослые) | ФИО, дата рождения, гражданство, документ | `order_passenger`, `purchase_revision_participant` |
| Несовершеннолетний (менеджерская заявка) | то же + свидетельство о рождении; связь с родителем/опекуном и подтверждение полномочий | ⟦новое; TOUR-79/80⟧ |
| Покупка/договор | Заявка, ревизии, цены строк, принятые редакции оферты/согласия с hash, время акцепта | `purchase`, `purchase_revision`, `orders.contract_snapshot` |
| Платежи | id операций банка, суммы, статусы, `providerPaidAt`/`knownAt`, способ (карта/СБП), без реквизитов карты | ⟦TOUR-77/78⟧ |
| Фискальные документы | ссылки на чеки, email для чека, признаки расчёта | ⟦TOUR-77/83⟧ |
| ЕИС | номер электронной путёвки/квитанция, пакет сведений, версия material revision | `order_eis`, `order_eis_event` |
| Уведомления | email, ключ outbox, статус доставки | `email_outbox` |
| Технические | IP (rate-limit, не сохраняется), токен SmartCaptcha (не сохраняется), cookie сессии | память процесса; отдельно — прямой трафик виджета CAPTCHA из браузера к Яндексу (§2) |

| Цель | Основание ⟦LEGAL⟧ | Данные |

| Заключение и исполнение договора, включая депозит, остаток, изменения, перенос | п. 5 ч. 1 ст. 6 152-ФЗ | все категории §1, кроме технических |
| Передача в ЕИС, фискализация, бухгалтерский учёт | п. 2 ч. 1 ст. 6 (обязанность по закону) | спецификация ЕИС; платёжные/фискальные |
| Напоминания об остатке и просрочке | исполнение договора (информационные сообщения, не реклама) | email, номер заказа, сумма |
| Защита от злоупотреблений | законный интерес ⟦LEGAL: допустимость, раскрытие⟧ | IP в памяти, токен CAPTCHA |

| Реклама | отдельное согласие, не условие покупки | — |

Согласие (если требуется для конкретной операции) — отдельный обязательный флажок, не
объединённый с офертой; система хранит редакцию, hash, номер заказа и время (как в v1.0).

## 4. Хранение — классы вместо «не FULL → удалить за 24 часа»

Правило старой схемы (удаление неоплаченной брони) не подходит частично оплаченному действующему
договору. Предлагаемые классы (сроки назначают TOUR-45/TOUR-93 и юрист, документ их не задаёт):

| Класс | Пример | Начало отсчёта | Действие по окончании |
| --- | --- | --- | --- |
| R0 неоплаченное истёкшее удержание | нет подтверждённого платежа, read-back подтвердил отсутствие оплаты | закрытие операции | удаление данных туристов; сохранение минимального технического следа попытки ⟦срок⟧ |
| R1 действующий договор с депозитом | есть подтверждённый взнос | — | хранится как договор |
| R2 расторжение с незавершённым возвратом / UNKNOWN | спорные операции | урегулирование | хранение до подтверждения + срок доказывания |
| R3 оказанная услуга | SERVICE_RENDERED подтверждён | дата окончания услуги | сроки бухгалтерского/налогового учёта, исковой давности ⟦LEGAL⟧ |
| R4 законное удержание | спор, запрос органа | снятие hold | по общему классу |
| R5 ЕИС-сведения | номер путёвки, пакет | по правилам ЕИС ⟦LEGAL⟧ | — |

Механизм прекращения хранения и восстановления из бэкапов должен переиспользовать примитивы
TOUR-94 (lawful hold, ledger, reapply-after-restore), а не строить второй.

## 5. Узкий операторский доступ к документам (TOUR-79 / ручная ЕИС)

Требования к проекту (не разрешение доступа):

1. Роль: отдельная capability `identity_view` / `identity_correct`, выдаётся OWNER поимённо; EDITOR
   контента её не имеет.
2. Scope: только туристы конкретной брони/пакета, открытой оператором по номеру заказа; нет
   поиска по ФИО/номеру документа, нет списков по выезду с документами, нет массового экспорта.
   Исключение — формирование пакета для поставщика/ЕИС в объёме спецификации, отдельное действие.
3. Показ полных реквизитов только по явному действию «показать» с причиной; по умолчанию —
   маска (последние 2–4 символа номера).
4. Каждый просмотр и исправление — запись `admin_audit` (кто, когда, какая бронь, какие поля,
   причина) **без значений документов**; исправление создаёт новую ревизию с прежней историей.
5. Значения документов не попадают в логи, ошибки, URL, аналитику, Git, Plane, Refref; ответы
   `Cache-Control: no-store`.
6. TOTP step-up для просмотра; сессия Admin с короткими сроками (действующая 0011).
7. Сроки хранения журнала доступа — TOUR-93.

## 6. Что требуется до approve

1. Юридическая квалификация ролей получателей §2 и оснований §3; решение о необходимости
   согласия для каждого потока.
2. Минимальный набор полей Alfa `register` и Ferma (TOUR-83, без реальных операций до разрешения).
3. Спецификация ЕИС по видам выездов (TOUR-80) — определяет обязательные поля формы.
4. Обновление Политики и согласия (новые редакции, отдельные от оферты). Если SmartCaptcha
   включается — раскрыть оба потока (браузер → Яндекс и Commerce → Яндекс), основание и
   получателя до загрузки виджета; включение остаётся эскалацией после наблюдаемого abuse.
5. Сроки классов R0–R5 (TOUR-45/93).
