# TOUR-94 · Контракт прекращения хранения и обезличивания истории SSR/Admin

- **Статус:** PROPOSED (этап 1 из 3: контракт → код → синтетическая приёмка). Документ не
  утверждает конкретный механизм исключения из immutable history, не резервирует номер миграции,
  не разрешает production-удаления и не открывает Phase B.
- **Задача:** [TOUR-94](https://app.plane.so/art-workspace/browse/TOUR-94/); связаны
  [TOUR-93](https://app.plane.so/art-workspace/browse/TOUR-93/) (регламент сроков хранения),
  TOUR-67 runbook §2.3-B, [политика конфиденциальности SSR/Admin](../legal/2026-10-30-ssr-admin/privacy-policy.md).
- **Граница с TOUR-45:** персональные данные заказов/туристов/платежей вне scope. Примитивы этого
  контракта (lawful hold, ledger, reapply-after-restore) проектируются переиспользуемыми, чтобы
  TOUR-45 не строил второй retention/erasure-механизм. Одновременно TOUR-45 не запускать.
- **CUSTODY_IMPACT:** NO для этого документа. Установка, миграция и любые удаления на хосте —
  только по отдельной конкретной OWNER-авторизации.

## 1. Термины

| Термин | Значение | Что НЕ означает |
| --- | --- | --- |
| Снятие с публикации | материал исчезает из `public_*` views, SSR и кэшей | удаление payload из БД/истории/бэкапов |
| Прекращение хранения (erasure) | payload, необходимость в котором отпала, необратимо отсутствует во всех разрешённых местах хранения, проекциях, истории и экспортах | «Пометили удалённым», `setDisabled`, истечение TTL, `is_listed=false` |
| Минимизация | из записи удаляются поля, не нужные для сохраняющейся цели; остаётся минимальное событие | сохранение исходного payload под другим именем |
| Lawful hold | конкретное законное основание сохранить данные (спор, запрос органа, обязательный срок) | общее «может пригодиться» или «период эксплуатации продукта» |
| Erasure ledger | минимальная независимая запись решений об erasure (ids, версии, основание, полномочия, время) без payload | бэкап или копия удалённого содержания |
| Tombstone | фиксированный документ-заместитель стёртого payload | — |

Нельзя заявлять уничтожение по факту `setDisabled`, отзыва сессии, снятия с публикации или
истечения TTL (TOUR-94 описание). Сохранённый старый hash сам по себе не доказывает обезличивание.

## 3. Операция erasure — обязательные свойства

1. **Полномочия:** только OWNER с действующим TOTP step-up через отдельную SECURITY DEFINER
   функцию; EDITOR не может стирать или снимать hold. Отдельная NOLOGIN-роль/grant только на
   эту функцию (least privilege), без прямых UPDATE/DELETE прав.
2. **Явный scope:** `item_id` + перечисление затронутых хранилищ из §2 (по умолчанию — все E для
   данного item, включая связанные media). Неизвестный/частичный scope — отказ.
3. **Основание:** код основания (`PURPOSE_ENDED`, `CONSENT_WITHDRAWN`, `SUBJECT_REQUEST`,
   `UNLAWFUL_PROCESSING`) и ссылка на внешний запрос/решение без ПД в самой строке.
4. **Lawful hold:** при активном hold на item/media — отказ `LAWFUL_HOLD`, без частичных изменений.
   Hold фиксирует основание, срок пересмотра и кто установил; сам hold не содержит payload.
5. **Идемпотентность:** `request_id`; повтор с тем же scope → прежний результат; тот же
   `request_id` с другим scope → отказ.
6. **Атомарность:** снятие публикации, замена payload во всех строках БД, запись ledger и
   постановка задач worker (S3, кэш) — одна транзакция; внешние удаления подтверждаются
   worker'ом, неподтверждённое — видимое состояние `ERASURE_PENDING_EXTERNAL`, не «выполнено».
7. **Минимальная запись события:** `{erasure_id, request_id, item_id, kind, versions_affected,
   stores_affected, basis, authorized_by (admin_id), authorized_at, ledger_seq, prev_ledger_hash}` —
   без payload, без исходного hash payload.
8. **Без обратимого остатка:** после операции ни одна таблица/представление/экспорт не позволяет
   восстановить payload; hash-коммитменты к стёртому payload не остаются в открытом виде.
9. **Неизменяемость прочей истории:** триггеры immutability сохраняются для любых иных
   изменений; старые миграции, триггеры и доказательства не переписываются; legal_publication и
   платёжные/фискальные записи не затрагиваются.

## 4. Варианты механизма исключения из immutable history (выбор — на этапе кода)

| # | Механизм | Плюсы | Минусы/риски |
| --- | --- | --- | --- |
| 4.1 | **Узкое исключение в триггере:** UPDATE ревизии разрешён только внутри erasure-функции (transaction-local маркер, совпадающий с ledger-строкой той же транзакции) и только переходом `document → tombstone`, `document_sha256 → hash(tombstone)` | Минимальная forward-миграция, существующие запросы работают | Требует аккуратной защиты маркера от подделки (только SECURITY DEFINER), тестов на все прочие UPDATE |
| 4.2 | **Разделение payload:** ревизия хранит ссылку и солёный коммитмент, payload и соль — в отдельной стираемой таблице; удаление строки payload уничтожает соль | Ревизия остаётся байт-в-байт неизменной; коммитмент без соли не подбирается | Крупная миграция существующих ревизий, изменение всех read-путей |
| 4.3 | **Crypto-shredding:** payload зашифрован ключом на item, ключ в отдельной таблице | Стирание = удаление ключа | Ключ попадает в те же бэкапы — без reapply ledger ничего не даёт; управление ключами — custody impact |

Для `admin_audit` (MAC-аттестация) отдельно выбрать: переаттестация минимизированной строки
новым ключом с записью erasure_id, либо сохранение исходного MAC с явным флагом «минимизировано
по erasure_id» и проверкой аттестации, знающей об этом. Нельзя оставить строку, проверка которой
молча падает или проходит по старому содержанию.

**Семантика доказательств после обезличивания.** Минимизированная запись — это *производная*
запись, а не исходная: она обязана нести видимую пометку `MINIMIZED(erasure_id, at)`, ссылку на
ledger-событие и аттестацию, которая утверждает только «эта минимизированная форма получена
операцией erasure_id», но не «так выглядело исходное событие». Проверка, не знающая об
erasure, должна видеть запись как изменённую, а не как подлинный оригинал. В экспорте/выдаче
доказательств такие записи явно маркируются.

Рекомендация к обсуждению: 4.1 для Phase B (минимальная поверхность изменений) с явным запретом
сохранять исходный `document_sha256`; 4.2 — если ревью сочтёт неизменность байтов ревизии
обязательной. **4.1 не утверждается без threat model** (§4.1-T). Решение фиксируется в PR этапа 2.

### 4.1-T. Threat model узкого исключения (обязательна до выбора 4.1)

| Угроза | Требуемая защита | Проверка |
| --- | --- | --- |
| Подделка transaction-local маркера (`SET LOCAL`/`set_config`) обычной ролью | маркер сам по себе не даёт права: триггер требует ledger-строку той же транзакции (`xmin`/txid), вставить которую может только SECURITY DEFINER функция erasure; GUC-имя не является секретом | тест: роль admin_app/commerce_app выставляет маркер и пытается UPDATE ревизии → отказ |
| Вызов привилегированной функции в недопустимом контексте (EDITOR, без TOTP step-up, повторно в той же транзакции с другим scope, из другой SECURITY DEFINER функции) | EXECUTE только у отдельной роли; проверка authority/step-up внутри функции; один erasure на транзакцию; `search_path` закреплён | sabotage-тесты на каждый guard |
| Перезапись ревизии не в tombstone (произвольный payload под видом erasure) | триггер допускает ровно переход `document → tombstone фиксированной формы` и `document_sha256 → hash(tombstone)`; прочие колонки неизменны | тест: иной target-документ → отказ |
| Удаление/подмена записей ledger | ledger append-only, hash-chain, тот же триггерный режим, что у истории | тест цепочки |
| Обход через прямой UPDATE владельцем/суперпользователем | вне модели (операторская ответственность), но фиксируется в readiness-проверке целостности цепочки | сверка ledger ↔ состояние ревизий |

## 4А. Логическое прекращение доступности и физическое уничтожение

Это разные операции с разными подтверждениями и статусами; одна не выдаётся за другую.

| Носитель | Логическое прекращение (T1, синхронно) | Физическое уничтожение (асинхронно) | Подтверждение |
| --- | --- | --- | --- |
| Строки БД (draft/current/revisions) | tombstone в транзакции erasure | освобождение страниц: `VACUUM`; старые версии строк до vacuum/WAL-ротации ещё существуют физически | статус `LOGICAL_DONE` сразу; `PHYSICAL_DONE` после vacuum + истечения WAL/PITR-окна |
| S3 варианты/noncurrent | снятие публичного доступа, удаление текущих объектов | удаление noncurrent версий, lifecycle-подтверждение провайдера | read-back отсутствия объектов и версий |
| Кэши SSR/regional/CDN | инвалидация | истечение максимального TTL кэша | время T1 + max TTL, проверка отсутствия ответа |
| Логи контейнеров/прокси | — (payload в логи не пишется) | ротация | проверка отсутствия маркеров |
| Зашифрованные dump | reapply ledger при любом восстановлении | уничтожение по ротации; иначе блокирование | журнал ротации с датой выхода последнего dump, содержащего payload |

Ответ субъекту/OWNER различает «доступ и использование прекращены» (`LOGICAL_DONE`) и «все копии
уничтожены» (`PHYSICAL_DONE` с датой), а не объявляет уничтожение в момент T1.

## 5. Резервные копии и восстановление

Ledger должен быть **независим от цепочки бэкапов БД**: иначе восстановление T0 откатывает и
сами решения об erasure. Простое размещение off-host недостаточно — ledger сам требует гарантий:

- **Целостность:** append-only записи с монотонным `ledger_seq` и hash-chain
  (`entry_hash = H(prev_hash ‖ entry)`); последний `head_hash` периодически фиксируется в
  независимом месте (например, в Plane/инфраструктурном receipt без payload) для обнаружения
  обрезки хвоста.
- **Сохранность:** минимум две независимые копии (в БД и off-host), запись в off-host —
  подтверждаемая (write + read-back hash) до объявления `LOGICAL_DONE`; при недоступности
  off-host erasure остаётся `PENDING_LEDGER_EXPORT`, а не «выполнено».
- **Синхронизация:** readiness сверяет `head_hash`/`ledger_seq` БД и off-host копии;
  расхождение (пропуск, перезапись, форк цепочки) — `NOT_READY`, ручное расследование.
- **Защита от перезаписи:** off-host хранилище с версионированием/WORM-режимом, если провайдер
  его поддерживает; права на запись — только у отдельной учётной записи экспорта.

- Каждая запись ledger (без payload) дополнительно записывается в отдельное off-host
  append-only хранилище с собственной ротацией (конкретное место и authority — custody, VPS-15).
- После любого restore: Commerce, Admin API и media worker стартуют в `NOT_READY`
  (`ERASURE_LEDGER_UNRECONCILED`), пока все записи ledger новее точки восстановления не
  переприменены и сверка (§7, шаг 6) не прошла. Ingress и worker не запускаются раньше —
  иначе worker может переопубликовать восстановленный из T0 `source_bytes`.
- Неполная сверка — NO-GO, сервис остаётся закрытым.
- Старые дампы уничтожаются по ротации; если в законный срок невозможно — блокирование до
  уничтожения (политика конфиденциальности, ч. 6 ст. 21 152-ФЗ).

## 6. Учётные записи и сессии (связь с TOUR-93)

`setDisabled`/отзыв сессии — ограничение доступа, не прекращение хранения. Для accounts/sessions
нужна та же операция с классом M: по истечении окна проверки инцидентов сессии удаляются или
обезличиваются, логин отключённого пользователя псевдонимизируется, а в `editorial_audit`,
`admin_audit`, `media_event` остаётся стабильный нейтральный идентификатор, достаточный для
связи действия с полномочием. Какие идентификаторы и сколько хранить — решает TOUR-93; этот
контракт требует, чтобы решение было исполнимо той же процедурой и попадало в ledger.

## 7. Синтетическая приёмка (этап 3, только одноразовая БД)

1. Синтетический организатор + отзыв + отчёт с фото, ≥ 3 версии, ссылки из departure.
2. **Backup T0** (тем же инструментом, что production logical dump).
3. **T1:** erasure по OWNER, проверка отказа EDITOR, отказа при hold, идемпотентного повтора,
   конфликта request_id/scope.
4. После T1 payload отсутствует в: `content_item*`, ревизиях, Admin API history/экспорте,
   `public_*`, SSR-ответе, S3 (включая noncurrent), логах; поиск по уникальным синтетическим
   маркерам и по известным hash исходного payload — 0 совпадений.
5. Ledger-запись сохранена независимо от БД.
6. **Restore T0** в изолированную БД → сервисы `NOT_READY` → **reapply T1** из ledger → повтор
   проверки шага 4 → только после PASS — ingress/worker.
7. Sabotage-проверка: отключение каждого guard (hold, роль, маркер триггера, readiness-гейт)
   должно ронять свой тест.

До PASS реальный сторонний контент (организаторы, отзывы — TOUR-95) запрещён. Phase A
по-прежнему допускает только служебные учётные записи и две утверждённые legal-редакции.

## 8. Миграция и владение SQL

Любое изменение схемы — одна append-only forward-миграция после перечитывания канонического
`commerce/migrations/journal.json` и `migration.lock` в момент реализации. Номер не
резервируется этим документом: денежный поток TOUR-77/78 может занять ближайший. Миграцию
ведёт единственный владелец SQL этого потока; параллельных конкурирующих миграций нет.
