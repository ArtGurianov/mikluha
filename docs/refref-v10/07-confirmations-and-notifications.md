# Подтверждения и уведомление организатора (M6.4)

Статус: **проект целевого контракта для review — подготовка к реализации, а не её выполнение.** Это целевая спецификация бывшей вехи **M6.4 «Confirmations and organizer notification»** (историческое Linear-происхождение ART-267, текущее задание [TOUR-31](https://app.plane.so/art-workspace/browse/TOUR-31/)). Документ описывает **требуемое поведение**, а не уже обслуживаемый API. Код, SQL, установленная схема, настройки провайдеров и продажи этим документом не изменяются; онлайн-бронирование закрыто, платёжный worker не запущен ([commerce/README](../../commerce/README.md)).

**TOUR-31 остаётся открытой (Backlog).** Этот PR — только design-контракт. Собственный outbox новых типов сообщений, worker/доставка, шаблоны писем и их тесты (сценарии §8 имеют статус NOT_RUN) остаются **реализационным scope самой TOUR-31** и не передаются в TOUR-78/79 целиком: TOUR-78/79 дают денежные/договорные факты-триггеры (депозит, остаток, FULL, ревизии, перенос), а транспорт уведомлений по этим фактам реализует TOUR-31. Запрет включать продажи не запрещает разрабатывать неактивный runtime; отсрочку оправдывает только отсутствие назначения и статус Backlog, а не этот документ.

Денежная модель — [02](02-booking-and-prepayments.md); сроки и параметры OWNER — [MK-POLICY-v2.4](06-mk-policy-v2.4.md); фискальные/ЕИС/правовые границы — [04](04-fiscal-eis-and-legal-impact.md).

## 1. Что покрывает M6.4

Исходящие покупательские и операторские сообщения, порождённые денежными и договорными фактами одной покупки:

1. покупательское **подтверждение поступления денег** (депозит/взнос) и, **отдельным логическим событием**, подтверждение **действительной оплаченной брони** (см. §1.1);
2. **квитанция о доплате** (top-up) и подтверждение **полной оплаты** (истинный FULL по эффективной ревизии);
3. **напоминания об остатке** (T−7 суток, T−48 часов) и **уведомление о наступившей просрочке** (T−24) с контактом менеджера;
4. **извещения об изменении** принятой ревизии: равноценная замена исполнения, согласованная договорная ревизия, продление срока долга, предложение переноса и его исход, возврат/переплата;
5. **уведомление организатора/менеджера о новой оплаченной брони**.

M6.4 — это транспорт уведомлений и его идемпотентность, а **не** источник денежных/правовых фактов. Сообщение отражает уже зафиксированный durable факт; оно не создаёт, не подтверждает и не ускоряет обязательство. Фактические события определены в [02 §4–§8](02-booking-and-prepayments.md) и [MK-POLICY §3](06-mk-policy-v2.4.md).

### 1.1. «Деньги получены» ≠ «бронь подтверждена»

Денежная модель v10 различает получение денег, действительность принятой ревизии и закрепление мест ([02 §3](02-booking-and-prepayments.md)). Поэтому M6.4 различает **два логических события**, которые нельзя считать тождественными по умолчанию:

- **DEPOSIT_RECEIVED / PAYMENT_RECEIVED** — доказанное относимое поступление денег по покупке (qualified provider read-back, [02 §4.5](02-booking-and-prepayments.md)). Это квитанция о деньгах.
- **BOOKING_CONFIRMED** — действительная оплаченная бронь: назначение операции отнесено к принятой эффективной ревизии, места закреплены договорной бронью, нет открытой сверки назначения/места. Только это событие даёт покупателю формулировку «Бронирование подтверждено».

Они могут наступать одновременно (и тогда покупатель получает одно письмо), но при расхождении — деньги пришли, а назначение операции или состояние места ещё требуют сверки (UNKNOWN/спорное место, [02 §4.7, §6](02-booking-and-prepayments.md)) — отправляется только квитанция о поступлении, **без** подтверждения брони, до завершения сверки. Нельзя писать «бронь подтверждена» на одном факте прихода денег.

## 2. Что переносится из существующего outbox, а что предстоит реализовать

Целевая реализация опирается на два уже существующих атомарных Postgres-outbox, но они **различаются**, поэтому требование нельзя выдавать за автоматически унаследованное свойство: [`email.ts`](../../commerce/src/email.ts) (подтверждение, миграция 0005) хранит `recipient_email` и `access_token` **в строке сообщения** (обнуляются при retention/успехе, [`orders.ts`](../../commerce/src/orders.ts) `maintain`), а [`execution-notice.ts`](../../commerce/src/execution-notice.ts) (миграции 0009/0010) **не хранит получателя** и читает его из `order_contact` в момент отправки.

**Переносимые инварианты** (действуют в обоих и обязательны для новых типов):

- **Атомарность факта и обязательства.** Строка outbox пишется в той же локальной транзакции, что и доказанный денежный/договорный факт ([02 §4.6](02-booking-and-prepayments.md)); нет сообщения без факта и факта без обязательства его сообщить. Сетевой вызов провайдера — вне транзакции, в отдельном worker.
- **У Notisend нет ключа идемпотентности.** Автоматически повторяется только отправка, доказанно `NOT_SENT` (до соединения — запрос процесс не покинул). Любой исход, который мог быть поставлен в очередь (`AMBIGUOUS`: таймаут, 5xx, нечитаемый ответ, оборванная передача), уходит в `ATTENTION` и **никогда не отправляется второй раз автоматически**; `REJECTED` и исчерпание бюджета ретраев `NOT_SENT` — тоже `ATTENTION`.
- **Стабильный `X-Mikluha-Outbox-Key`** едет заголовком для ручного сопоставления неоднозначной отправки с логом провайдера; это **не** ключ дедупликации на стороне Notisend.
- **Без ПД в логах:** логи несут только ссылки на заказ/покупку и коды.

**Изменения схемы/retention, которые предстоит реализовать** (не свойство текущего кода):

- **Получатель читается в момент отправки**, а не хранится в строке сообщения (как уже делает `execution-notice`, но **не** `email.ts`). Это требование к новой схеме новых типов; стёртый по retention контакт даёт `ATTENTION` c кодом `NO_RECIPIENT`, а не отправку.
- **Отдельная строка и ключ на каждый тип сообщения** (§3): текущая `email_outbox` с `UNIQUE (order_id, type='BOOKING_CONFIRMATION')` покрывает только одно подтверждение на заказ и для новых типов forward-only расширяется отдельной реализацией.
- **Потребитель отчётов о доставке** (`ACCEPTED → DELIVERED`, §4): storage-примитив `recordNoticeDelivery` есть, но runtime-потребитель не подключён (историческое ART-365).

Иначе документ завысил бы степень повторного использования существующего кода.

## 3. Независимая идемпотентность, актуальность и идентичность сообщения

Каждое сообщение — **отдельная строка outbox со своим стабильным ключом**, выведенным из породившего durable-факта, а не из жизненного цикла покупки целиком. Один платёж, одна ревизия, один срок порождают ровно одно логическое сообщение своего типа; повторный callback, restart worker или ретрай того же взноса не создают второе.

**Логическая идентичность сообщения** (для дедупликации) — тройка `eventType`, `factId`, `recipientRole`; строковый ключ — её проекция. `recipientRole` различает покупателя и оператора. `templateVersion` — **неизменяемый атрибут уже сформированного сообщения** (редакция шаблона на момент постановки, для аудита), а **не** часть идентичности: публикация новой версии шаблона сама по себе не порождает второе сообщение по уже обработанному факту. Повторное уведомление по тому же факту допускается только отдельным явно обоснованным `eventType`/событием.

| `eventType` | Триггер (durable факт) | `factId` → форма ключа |
|---|---|---|
| `DEPOSIT_RECEIVED` / `PAYMENT_RECEIVED` | Доказанное относимое поступление | `operationId` → `payment:<operationId>` |
| `BOOKING_CONFIRMED` | Действительная оплаченная бронь (§1.1) | `purchaseRef` → `booking-confirmed:<purchaseRef>` |
| `FULL_PAID` | Первый действительный FULL по эффективной ревизии ([02 §5](02-booking-and-prepayments.md)) | `purchaseRef`+`effectiveRevisionRef` |
| `BALANCE_REMINDER` | Плановый момент T−7d / T−48h при положительном остатке | `purchaseRef`+`assertedDueAt`+`kind` |
| `BALANCE_OVERDUE` | Плановый срок долга при положительном остатке | `purchaseRef`+`assertedDueAt` |
| `REVISION_ACCEPTED` / `EXECUTION_CHANGE` / `DEADLINE_EXTENDED` | Принятая ревизия / классиф. изменение исполнения / append-only продление срока | тип+`revisionRef`\|`changeId`+`orderId` |
| `TRANSFER_OFFER` / `TRANSFER_OUTCOME` | OPEN-предложение и его COMMITTED/CLOSED/NEEDS_RESOLUTION ([02 §7.2](02-booking-and-prepayments.md)) | `proposalRef`+`phase` |
| `REFUND_SETTLED` | Доказанно успешный относимый возврат | `refundOperationId` |
| `OVERPAYMENT_ESTABLISHED` | Установленная переплата **без** фактического возврата | `overpaymentFactId` (не `refundOperationId`) |
| `ORGANIZER_BOOKING` | `BOOKING_CONFIRMED` по покупке (§6) | `purchaseRef`+`milestone` |
| `ORGANIZER_PAYMENT_RECEIVED` | Опционально: поступление денег до подтверждения брони (§6) | `purchaseRef`+`operationId` |

Уточнения к прежней версии таблицы: возврат и переплата — **разные** `eventType` с разными `factId` (переплата без возврата не имеет `refundOperationId`); одна ревизия может порождать **несколько** разных извещений — каждый тип отдельным сообщением и ключом, а не один `revision:<revisionRef>`.

Правила актуальности и ключей:

- **Ключ привязан к факту, а не ко времени worker.** Поздно доставленный банковский результат восстанавливает фактическую хронологию ([02 §5](02-booking-and-prepayments.md)); он не порождает дубль и не передатирует уже отправленное.
- **UNKNOWN не уведомляется как оплата.** Пока исход операции не доказан, сообщение об успехе/остатке не ставится; напоминания учитывают открытые/UNKNOWN операции ([MK-POLICY §3](06-mk-policy-v2.4.md)).
- **Атомарная отмена устаревших напоминаний.** `BALANCE_*` несут `assertedDueAt`/версию графика. При авторизованном продлении срока (append-only `DEADLINE_EXTENDED` без новой ревизии, [MK-POLICY §1](06-mk-policy-v2.4.md)) в **той же локальной транзакции**, что фиксирует новое событие срока: (1) ещё не захваченные `PENDING` напоминания со старым `assertedDueAt` переводятся в терминальное `SUPERSEDED` (не `ATTENTION`), (2) пересчитываются и ставятся ещё применимые напоминания по новому сроку. Дубль по новому сроку не создаётся за счёт ключа (`…+assertedDueAt`).
- **Повторная проверка при claim/dispatch.** Перед отправкой worker **ещё раз** сверяет, что `assertedDueAt`/версия графика сообщения всё ещё актуальны (и остаток положителен, без подтверждённой полной оплаты); устаревшее сообщение не отправляется, а переводится в `SUPERSEDED`. Это закрывает окно между постановкой и отправкой.
- **Гонка с `SENDING`.** Сообщение, уже захваченное в `SENDING` (lease) к моменту commit изменения срока, нельзя «отозвать». Контракт: (1) окно claim→send ограничено коротким lease; (2) актуальность `assertedDueAt` перепроверяется в последней точке перед вызовом провайдера в рамках того же lease; (3) если устаревшее обязательство всё же ушло, оператору поднимается флаг и покупателю отправляется корректирующее сообщение с новым сроком. Основная защита — атомарная отмена `PENDING` и перепроверка при dispatch; остаточная гонка явно признана и ограничена, а не замолчана.

## 4. «Принято» (acceptance) ≠ «доставлено» (delivered)

Документ последовательно различает три разных смысла, которые нельзя сливать:

1. **Договорное принятие** — покупатель/Mikluha приняли ревизию/оферту ([02 §7.1](02-booking-and-prepayments.md)). Бизнес-факт, не состояние сообщения.
2. **Провайдер принял сообщение (`ACCEPTED`)** — Notisend поставил письмо в очередь (`queued/sent/delivered` в ответе создания). Это **только** приёмка провайдером; доказательством доставки, прочтения или оказания услуги она не является. Как `FULFILLED` в старом checkout подтверждает бронь, а не поездку ([02 §3](02-booking-and-prepayments.md)), так `ACCEPTED` подтверждает приём письма, а не его доставку.
3. **Доставлено (`DELIVERED`)** — только при **проверенном отчёте провайдера о доставке**, коррелированном по `provider_job_id`. Отчёт переводит `ACCEPTED → DELIVERED`, bounce — в `ATTENTION` (как уже моделирует `recordNoticeDelivery`, [`execution-notice.ts`](../../commerce/src/execution-notice.ts)). Runtime-потребитель отчётов пока не подключён (историческое ART-365): storage-примитив, активируемый отдельно, с проверкой источника статуса.

Состояния строки сообщения: `PENDING → SENDING → ACCEPTED (→ DELIVERED)`; либо `→ ATTENTION`; либо `→ SUPERSEDED` (устаревшее, §3). Мониторинг и приёмка оперируют этими состояниями раздельно; «отправлено покупателю» в отчётности означает доказанное состояние сообщения, а не предположение о получении.

## 5. Завершение сообщения при ATTENTION

Идемпотентность защищает от дублей, но **не** обеспечивает завершение уведомления: `ATTENTION` означает, что автоматический повтор запрещён, а не что обязательство исполнено. Для сообщений, критичных покупателю (подтверждение брони, просрочка, исход переноса/возврата), требуется операторский процесс завершения:

1. **Сверка по provider job/log** по `X-Mikluha-Outbox-Key`/`provider_job_id`: было ли сообщение фактически отправлено/доставлено, или отправки не было.
2. **Документирование результата сверки** (отправлено/не отправлено/доставлено/bounce) с источником доказательства.
3. **Разрешённое ручное действие**: при доказанном отсутствии отправки — отдельная ручная повторная отправка (новая попытка с тем же логическим фактом, под контролем оператора, не автоматическая); при доказанной отправке — повтор запрещён, фиксируется как исполненное.
4. **Аудит решения**: actor, основание, время, исход — неизменяемой записью.
5. **Порядок при отсутствии доказательства доставки**: обязательство остаётся незакрытым и видимым в мониторинге; молчаливое закрытие `ATTENTION` без сверки запрещено. Для критичных денежных сроков допустим альтернативный канал связи с покупателем через менеджера.

Ручная повторная отправка не обходит правило Notisend: она допустима только после доказанного `NOT_SENT`/отсутствия отправки, а при неоднозначности сначала выполняется сверка.

## 6. Уведомление организатора о новой оплаченной брони

Отдельное **внутреннее операторское** сообщение (`recipientRole=operator`) организатору/менеджеру о появлении новой оплаченной брони. Оно независимо от покупательского подтверждения, от Refref-outbox ([03](03-refref-integration.md)) и от ЕИС/фискальных событий ([04](04-fiscal-eis-and-legal-impact.md)) и само по себе не является ни квитанцией, ни передачей ЕИС, ни отчётом Refref.

- **Триггер — подтверждённая бронь, не поступление денег.** Основное уведомление `ORGANIZER_BOOKING` привязано к **`BOOKING_CONFIRMED`** (§1.1), а не к первому доказанному депозиту: организатору не сообщают о «новой оплаченной брони» раньше, чем бронь действительно подтверждена (назначение операции отнесено к принятой ревизии, места закреплены, нет открытой сверки). Отправляется **ровно одно** сообщение — веха `deposit` (первое подтверждение оплаченной брони по покупке). `milestone=full` (на первый действительный FULL) **не отправляется по умолчанию** и включается только отдельным явным решением профиля. Каждая включённая веха наступает один раз (ключ `…+milestone`).
- **Раннее сообщение о деньгах — отдельно и опционально.** Если операционно нужно известить организатора о поступлении денег **до** подтверждения брони, это **отдельный** `eventType` `ORGANIZER_PAYMENT_RECEIVED` со своим ключом, явно не выдаваемый за подтверждённую бронь; по умолчанию выключен.
- **Получатель** разрешается в момент отправки из операторской конфигурации/привязки выезда, а не из покупательского контакта; отсутствие адресата — `ATTENTION` `NO_RECIPIENT`.
- **Минимизация ПД.** Операционный минимум: ссылка на покупку/заказ, выезд и дата, число мест, роль/сумма в нужном объёме, защищённая ссылка в Admin. **Паспортные и контактные данные туристов не включаются**; доступ к ним — узкий операторский процесс ([MK-POLICY §9](06-mk-policy-v2.4.md), TOUR-35/80). Соответствует принципу неизбыточности ПД ([04](04-fiscal-eis-and-legal-impact.md), TOUR-84).
- **Семантика та же:** собственный идемпотентный ключ, `ACCEPTED ≠ DELIVERED`, неоднозначный исход — оператору (§5), без второй автоматической отправки.
- Уведомление **не открывает продажи**, не подтверждает оказание услуги и не заменяет ручную передачу ЕИС/фискальное закрытие.

## 7. Границы и зависимости

- Документационная ветка не создаёт кода, SQL, миграций, новых банковских/ПД-данных и не включает продажи. Реализация транспорта уведомлений — **scope TOUR-31**; денежные/договорные факты-триггеры квалифицируются с [TOUR-78](https://app.plane.so/art-workspace/browse/TOUR-78/) (депозит/остаток/top-up/FULL), [TOUR-79](https://app.plane.so/art-workspace/browse/TOUR-79/) (изменения/перенос); правовые/ЕИС/ПД тексты и основания — TOUR-80/84/35; фактическая Alfa/Ferma передача чеков — TOUR-5/9/33/83.
- Открытые gate MK-C05–C10 сохраняются: статус платёжной ссылки не доказывает приход денег/чек, срок до поездки не доказывает оказание услуги, категория «тур» не доказывает обязанность ЕИС.

## 8. Сценарии приёмки (NOT_RUN)

Продолжают нумерацию [05 §E2E](05-migration-and-e2e.md); текстовые сценарии до фактической реализации — NOT_RUN. Минимум evidence — как в [05](05-migration-and-e2e.md): SHA/schema identity, correlation/source IDs без ПД, HTTP/DB/outbox хронология, явная пометка synthetic/real scope.

| ID | Сценарий | Ожидаемый результат |
|---|---|---|
| MKV10-E2E-50 | Один доказанный депозит; callback и restart worker дублируют факт | Одна квитанция `PAYMENT_RECEIVED` (`payment:<operationId>`), одно уведомление организатора (`…:deposit`); второй отправки нет |
| MKV10-E2E-51 | Отправка письма вернула таймаут/5xx (AMBIGUOUS) | Сообщение в `ATTENTION`, авто-повтора нет; только `NOT_SENT` до соединения допускает авто-повтор |
| MKV10-E2E-52 | Провайдер принял письмо (`ACCEPTED`), затем проверенный отчёт о доставке | `ACCEPTED → DELIVERED`; bounce того же сообщения → `ATTENTION`, не повторная отправка |
| MKV10-E2E-53 | Положительный остаток; authorized продление срока, напоминание ещё `PENDING` | Старое напоминание → `SUPERSEDED` атомарно с событием срока; новое ставится по новому `assertedDueAt`; дубля нет |
| MKV10-E2E-53a | То же, но старое напоминание уже захвачено в `SENDING` | Dispatch перепроверяет `assertedDueAt`; устаревшее не отправлено; при остаточной гонке — флаг оператору и корректирующее сообщение |
| MKV10-E2E-54 | Контакт покупателя стёрт по retention до отправки | `ATTENTION` `NO_RECIPIENT`, без отправки и без ПД в логах |
| MKV10-E2E-55 | Деньги получены, но назначение/место требуют сверки | Отправлена только квитанция `PAYMENT_RECEIVED`; `BOOKING_CONFIRMED` **и** `ORGANIZER_BOOKING` не отправлены до завершения сверки |
| MKV10-E2E-55a | Уведомление организатора о новой брони | Отправлено по `BOOKING_CONFIRMED`, не на одном поступлении денег; операционный минимум без паспортных/контактных ПД туристов; одно сообщение `milestone=deposit`; `full` и раннее `ORGANIZER_PAYMENT_RECEIVED` — только при явно включённом профиле; независимо от покупательского письма, Refref-outbox и ЕИС |
| MKV10-E2E-55b | Новая версия шаблона опубликована после обработки факта | Второго сообщения по тому же `(eventType, factId, recipientRole)` нет; `templateVersion` остаётся атрибутом уже сформированного сообщения |
| MKV10-E2E-56 | Критичное письмо в `ATTENTION` | Сверка по provider log, задокументированный результат, допустимая ручная повторная отправка при доказанном `NOT_SENT`, аудит; без молчаливого закрытия |
| MKV10-E2E-56a | Установлена переплата без фактического возврата | `OVERPAYMENT_ESTABLISHED` с собственным `factId`; не использует `refundOperationId` и не выдаётся за возврат |
