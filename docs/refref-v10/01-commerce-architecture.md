# Mikluha Commerce vNext — архитектура под Refref v10

Дата: 27.10.2026. Статус: **проект для review**, не установленная схема и не разрешение открыть продажи. Существующие договоры и исторические ADR этим PR не переписываются. Основания и точные SHA — в [точке входа](README.md) и [source-baseline.json](source-baseline.json).

## 1. Выбранная граница

Mikluha становится владельцем бронирования, покупательского checkout, каждого взноса, возврата, исполнения услуги и фискализации. Refref владеет атрибуцией, BOUND, признанием одной комиссии и её окончательностью, S4/B2, реестром партнёрского долга и S3. Refref не хранит график туристических взносов и не проводит покупательские платежи.

Предоплата и последующая доплата — обязательный сценарий существующего бизнеса Mikluha. Их размеры, сроки и правила мест нельзя вывести из старого кода, примеров 30/70 или условий Refref. Они заполняются в версии политики Mikluha до допуска checkout. Наличие отдельного Commerce Mikluha не создаёт платный продукт Refref Commerce.

| Объект/операция | Владелец | Что получает другая сторона |
|---|---|---|
| Каталог, выезд, вместимость, туристы, покупательский договор | Mikluha | Refref получает неперсональные подходящие строки и согласованный временной контекст |
| Все взносы, возвраты и их доказательства | Mikluha и её квалифицированный платёжный источник | Refref получает исход покупки; при S4 — полный относимый доказательный снимок |
| Touch, правила кампании, BOUND | Refref | Mikluha сохраняет устойчивый результат и привязку до открытия оплаты |
| Комиссия C, FINAL, решение S4/B2 | Refref | Mikluha исполняет обязанности и сохраняет исходное основание |
| Банковский перевод партнёру | Mikluha | В Refref отчёт/исправление; при споре — относимые доказательства |
| ККТ, чек, зачёт аванса, ЕИС | Mikluha по выбранной юридической роли | Эти состояния не создают C и не подменяют PAID_IN_FULL |

## 3. Рассмотренные варианты

| Вариант | Решение | Причина |
|---|---|---|
| Оставить Refref-owned checkout и добавить несколько Refref-попыток | Отклонён | Противоречит merchant-native v10, переносит взносы в Core, создаёт риск повторной комиссии |
| Переписывать существующий order/snapshot при переносе или смене туриста | Отклонён | Уничтожает доказательство принятого договора и конфликтует с неизменяемыми триггерами |
| Стабильная экономическая покупка + принятые неизменяемые ревизии + отдельные операции Mikluha | Предлагаемая реализация | Поддерживает deposits, переносы и одно право Refref, сохраняя прежние доказательства |

Выбранная архитектурная граница Refref утверждена OWNER. Конкретная структура агрегатов ниже — **предложение для реализации Mikluha**, а не новые эндпоинты Core и не готовый SQL.

## 4. Минимальная доменная модель

| Сущность | Что хранит | Инвариант |
|---|---|---|
| Purchase | устойчивый `purchaseRef`, выбранный integration profile, связи с legacy order, BOUND | Один purchaseRef на одну экономическую покупку; смена номера технического заказа не меняет право |
| Booking revision | состав услуги/туристов, цены и скидки, график платежей, выезд, версия/хеш документов, согласие | Принятая ревизия неизменяема; material change требует новой версии и надлежащего согласия |
| Seat allocation | выезд, количество, состояния удержания/подтверждения/освобождения, версия | Capacity сериализована с редактором выезда; нет освобождения оплаченных или неопределённых мест по таймеру |
| Payment operation | provider/account/operation identity, сумма RUB, назначение взноса, фактическое время, outcome и evidence | UNKNOWN не означает failure; дедупликация по источнику и операции; повторное списание не предлагается вслепую |
| Allocation fact | связь поступления/возврата с покупкой и подходящими строками, версия доказательств | Деньги учитываются один раз; часть операции не распределяется сверх её суммы |
| Contract/fiscal/EIS facts | принятие, оказание, чек/его результат, применимость/подача ЕИС | Не выводятся из статуса реферальной комиссии |
| Refref delivery outbox | стабильная команда/результат по BOUND и FULL/NOT_PAID/CANCELLED | Durable business fact и исходящая запись атомарны; ретраи сохраняют событие и фактические даты |

Это может быть несколько компактных таблиц в существующем PostgreSQL. Новый микросервис, универсальный double-entry ledger, собственная система сертификатов или отдельная копия реестра Refref не требуются. Детали DDL и полномочия — предмет последующего source review. Legacy `orders` остаётся историческим неизменяемым документом, а не изменяемым контейнером нового договора.

Состояния ортогональны: **бронь**, **покупательский денежный остаток**, **исход конкретной операции**, **исполнение услуги**, **фискальный/EIS долг**, **доставка отчёта Refref**. Нельзя выразить всё одним PAID/FULFILLED. Неуспех доставки FULL не возвращает реально оплаченный заказ в неоплаченный и не создаёт вторую платёжную сессию.

## 5. Обычный путь

```mermaid
sequenceDiagram
    participant B as Покупатель
    participant M as Mikluha Commerce
    participant R as Refref v10
    participant P as Провайдер Mikluha
    B->>M: Подтверждение условий брони / допустимое действие
    M->>R: Зафиксировать BOUND до открытия оплаты
    R-->>M: Durable результат / восстановление по commandId
    M->>P: Первая платёжная операция (депозит)
    P-->>M: Подтверждённое поступление
    M->>M: Остаток, документ/фискальная задача по своему событию
    B->>M: Доплата
    M->>P: Операция на подтверждённый остаток
    P-->>M: Подтверждённое поступление
    M->>M: Первая действительная полная оплата + outbox
    M->>R: PAID_IN_FULL с фактическими датами и принятой ревизией
    R-->>M: Одно право на C; FINAL по S5
```

Диаграмма описывает реферальную покупку, не делает BOUND условием любой органической продажи. Для покупки без привязки действует обычный merchant checkout без отчёта organic в Refref. Если намеревались получить BOUND, но результат команды неизвестен, сначала восстановить этот результат; нельзя объявить отказ, потерять партнёра и открыть оплату как обход.

Точка BOUND — до первой **возможности** оплаты, включая создание счёта, payment link/session и банковской операции. Нельзя сначала принять депозит, а потом привязать оставшуюся сумму к партнёру. Refref outage до BOUND и после BOUND обрабатываются по разным условиям [интеграционного контракта](03-refref-integration.md).

## 6. Изменяемая бронь без изменения прошлых прав

До первого действительного FULL размер покупки может меняться по [порядку принятия ревизии](02-booking-and-prepayments.md#71-договорная-ревизия-и-реферальная-квалификация-до-первого-full): локальное договорное принятие и асинхронная реферальная квалификация — разные результаты. Отказ/UNKNOWN ревизии Refref не блокирует сам договор и безопасную доплату, не уничтожает депозит/BOUND и не означает автоматическое C=0. При доказанной непригодности фактической FULL-ревизии награда по ней не обещается; источник истины о составе/цене остаётся у Mikluha. После первого FULL C зафиксирована: новые туристы/доплаты её не увеличивают, обычные изменения не двигают замороженный якорь S5. Документы и сообщения покупателю отражают новую согласованную услугу отдельно от Refref anchor.

Перенос на другой выезд атомарно меняет **актуальное** распределение мест и создаёт принятую ревизию; старый выезд и старый snapshot остаются в истории. Согласованное продолжение сохраняет purchaseRef/BOUND даже при вынужденном полном возврате и повторной оплате. Полное прекращение и последующая самостоятельная новая покупка требуют новой идентичности и нового осознанного действия. Нельзя выбирать тип операции ради обнуления комиссии.

Для добавления туриста в существующую покупку второе право не создаётся. Отдельная самостоятельная подходящая покупка нового участника может получить собственный BOUND до его первого платежа. Правило нельзя использовать для перепривязки уже оплаченной части старой брони.

## 7. Что сохраняется, что заменяется

| Источник/гарантия Mikluha | Судьба в предлагаемом новом профиле |
|---|---|
| ADR v2.3: SSR/PostgreSQL, editorial publish/CAS, Admin MFA, readonly public projection | Сохранить цель; SSR не объявляется выполненным |
| Принятый contract snapshot, выданная цена, прежние документы | Сохранить байты/хеши; поправки — отдельной принятой ревизией |
| Старый Refref checkout/fulfilment ack/payment read-back | Сохранить для старых попыток; для новых v10 native provider truth и отдельная доставка Refref outcomes |
| 100% upfront и scalar payment/attempt на order | Заменить для нового профиля обязательной моделью deposits/topups |
| Старое EIS-on-PAID и привязка всех данных туристов к этому предположению | Заменить только после профильной юридической квалификации; первичные сведения не терять |
| quote/seat/cutoff/stop/UNKNOWN/immutable migrations, договорная цена | Сохранить гарантии; календарь взносов и новая реализация должны пройти свои проверки |
| Старые правила v9 reward/window из TOUR status | Не переносить в новые права; применять pinned v10. Старые права продолжают свой исходный профиль |

Это карта проектируемого перехода, не редактирование исторических ADR и не изменение действующей оферты. Реальная инвентаризация может выявить старые обязательства даже при отсутствии публичного старта.

## 8. Нагрузка и эксплуатация

Обычная продажа автоматическая: provider callback/read-back → локальный факт → outbox FULL → получение результата. Постоянного потока возвратов в Refref нет. Модератор не подтверждает каждый покупательский платёж и не ведёт календарь взносов.

Оператор видит только требующие решения исключения: UNKNOWN операции, неподтверждённое освобождение мест, просроченный остаток/согласование, фискальную ошибку, неполный EIS пакет, устойчивый отказ доставки. Уведомления и деньги имеют разные idempotency keys. Подтверждение отправки email не называется вручением, успешная фискализация — новым поступлением денег.

ПД и сканы документов не включаются в стандартный Refref outcome. Логи и мониторинг используют opaque IDs. Обычный адаптер не получает ключ оператора ЕИС, Admin, банка для выплат партнёру или финансовые полномочия Refref.
