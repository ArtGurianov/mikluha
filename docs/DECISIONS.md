# Архитектурные решения

Инварианты, которые в коде выглядят странно или избыточно, если не знать причину.
Это **не** ТЗ, не история изменений и не описание фич — только то, что нельзя
поменять, не сломав что-то неочевидное. Если решение здесь больше не имеет
смысла — его можно пересмотреть, но осознанно.

---

## 1. Публичный сайт — pure SSG, CMS нет в runtime пользователя

`output: "export"` + Nginx, отдающий статику. Никакого Node.js в runtime
публичного сайта.

**Исключение — серверная коммерция (#9).** Бронирование и оплата требуют сервера:
ключ Refref Business API не может жить в браузере. Это отдельный сервис
`mikluha-commerce`, а не runtime сайта: сайт остаётся статикой и продолжает
открываться, даже если коммерция остановлена.

**Почему:** публичный web-server должен быть дешёвым и предсказуемым: он отдаёт
только файлы, без Node.js и CMS runtime. Текстовый контент уже находится в
`/out`; WebP/WebM браузер запрашивает напрямую из Object Storage.

`/admin` тоже является статическим бандлом. Sveltia обращается прямо к GitHub
по отдельному repo-scoped PAT каждого редактора и прямо к Object Storage;
OAuth broker, serverless function и общий CMS secret отсутствуют.

**Где живёт:** `next.config.ts`, `Dockerfile` (stage 3 — только Nginx),
`public/admin/`, `scripts/validate-static-export.ts` (проверяет наличие обоих
статических бандлов и допустимость прямых media URL).

## 2. Медиа CMS используются напрямую, без обработки

CMS принимает WebP до 1 МиБ и WebM до 10 МиБ и записывает прямой Object Storage
URL в YAML. Next.js рендерит обычные `<img>`/`<video>`: без оптимизатора,
скачивания, перекодирования или генерации вариантов. Галереи ограничены десятью
изображениями.

**Почему:** обработка изображений увеличивала стоимость и время редких сборок.
Подготовка файлов перенесена на редактора, а Object Storage оптимизирован для
раздачи таких объектов. Hero-видео опционально; WebP остаётся poster/fallback,
для `prefers-reduced-motion` видео скрывается.

**Где живёт:** `public/admin/config.yml`, `lib/cms/asset-source.ts`,
`components/media/cms-image.tsx`, `components/home/hero.tsx`, validators.

## 3. Каждая сборка начинается с чистых generated-каталогов

`pnpm run clean` удаляет `.next`, `out`, `.cms-cache` и возможный legacy
`public/generated/cms` от старых checkout.

**Почему:** ассеты удалённого/заменённого контента не должны переезжать в
следующий релиз. Ephemeral-файловая система Docker-сборки — вторая линия
защиты: если в `clean` забудут добавить новый generated-каталог, контейнер всё
равно стартует с пустого места.

**Где живёт:** `package.json` (`clean` — первый шаг `build:production`).

## 4. `launchReady` + real contract data — production safety gate

Production-сборка (`DEPLOY_ENV=production`, значение по умолчанию) падает, пока
`siteSettings.launchReady` не включён, и падает повторно, если при включённом
`launchReady` где-то остался `isDemo=true`. Каждый OPEN-выезд должен иметь
`capacity` и полный набор договорных данных тура и выезда, совпадающий с
fail-closed правилами `mikluha-commerce`. Явный маркер «Демо» внутри этих полей
тоже блокирует сборку, даже если кто-то снял `isDemo`.

**Почему:** снять флаг проще, чем проверить маршрут, размещение, перевозчика и
поставщиков. Продажа демо-условий создаёт реальный договор с вымышленными данными,
поэтому содержимое проверяется как код, а не как пункт launch-чеклиста.

**Где живёт:** `scripts/validate-content.ts`. Демо-сборки — `DEPLOY_ENV=staging`.

## 5. Сайт не собирает пользовательские данные

Статический сайт по-прежнему не собирает ничего. Данные, без которых нельзя
продать поездку (заказ, туристы, контакт для чека), принимает и хранит только
`mikluha-commerce` (#9). Кнопка бронирования на сайте — обычная ссылка на этот
отдельный сервис.

На публичном сайте нет форм, аккаунтов, cookies, analytics и tracking SDK. Nginx
не пишет request-level логи. Commerce использует только необходимую защищённую
`__Host-mk_<order>` cookie, чтобы другой браузер не получил доступ к заказу, и
хранит отдельное версионированное подтверждение согласия на обработку ПД.

**Почему:** это продуктовое обещание, а не техническое ограничение. Оно же
позволяет держать простую и честную privacy-страницу.

**Где живёт:** `nginx.conf` (`access_log off`),
`components/booking/booking-button.tsx`, `commerce/src/web.ts`, отсутствие
analytics-зависимостей в `package.json`.

## 6. Содержимое content/ → normalize → внутренние DTO

UI-компоненты никогда не видят сырой YAML из `content/`. Между ними —
`normalize.ts`, который превращает распарсенные документы во внутренние DTO с
локальными путями к картинкам.

**Почему:** CMS можно заменить (уже заменили один раз — см. история этого
файла), не переписывая компоненты. Плюс это единственное место, где
принимаются решения «что значит отсутствующее поле».

**Где живёт:** `lib/cms/types.ts` (граница), `lib/cms/normalize.ts`.
`Raw*`-типы — руками написанные зеркала полей `public/admin/config.yml`;
схема-экстракции/typegen для git-based CMS не существует, поэтому
рассинхронизация схемы и типов теперь ловится не компилятором, а тем же
способом, что и всегда ловилась «настоящая» нехватка поля — падением
`normalize.ts` с именем документа.

## 7. Rebuild при публикации + по расписанию только в дни, когда выезд уходит в прошлое

Сайт пересобирается по публикации контента (push в `main`, «Опубликовать изменения» в `/admin`)
и дополнительно — по расписанию `.github/workflows/publish.yml`, сразу после полуночи по
`siteSettings.timezone`, **но только если вчера или позавчера начался какой-то выезд и `main` уже
целиком опубликован**. В остальные дни scheduled-запуск ничего не деплоит.

**Почему:** «ближайший выезд», статус набора и кнопка бронирования вычисляются во время сборки
(`getTodayInTimezone`). Без пересборки уехавшая группа оставалась на сайте как «Набор открыт» с
QR на оплату — это и устаревшая коммерческая информация для поисковиков, и деньги за поездку,
которая уже началась. Раньше cron отклоняли из-за отдельного deploy-credential на сервере, но
теперь Coolify-токен уже живёт в GitHub secrets для кнопки публикации, так что расписание ничего
нового не требует. Ежедневная безусловная сборка не нужна: контент без правок меняется только в
день после старта выезда.

**Scheduled-сборка никогда не публикует неопубликованные Save.** Любой deploy собирает текущий
`main`, а Save из `/admin` попадают туда `[skip ci]`-коммитами задолго до «Опубликовать
изменения» (см. «CMS publish» ниже). Поэтому расписание деплоит, только если `main` уже живой:
HEAD — обычный коммит (Coolify собрал его на push вместе со всеми Save до него) или ровно тот
коммит, который опубликовал последний успешный запуск «Опубликовать изменения» (`head_sha`
запуска `repository_dispatch`). Иначе ничего не деплоится, а запуск падает — GitHub присылает
письмо: сайт устарел, и только человек решает, можно ли выпускать накопленные Save. То есть
свежесть сайта — best effort, публикационная семантика CMS — инвариант.

Валидация контента намеренно не падает на OPEN-выезде в прошлом (только предупреждение), иначе
она блокировала бы именно ту сборку, которая его убирает.

**Где живёт:** `lib/tours.ts` (`getTodayInTimezone`), `.github/workflows/publish.yml` (`schedule`
и шаг-фильтр), `scripts/validate-content.ts` (предупреждение), `RUNBOOK.md` → «Периодичность
обновлений».

## 8. `isListed` и `bookingStatus` — две разные вещи

* `isListed` — показывать ли документ на сайте;
* `bookingStatus` (`OPEN`/`CLOSED`/`CANCELLED`) — бизнес-состояние выезда.

(Раньше был и третий, редакционный статус — состояние публикации в Sanity. У
Git-based CMS такого состояния нет: коммит в `main` немедленно считается
опубликованным, если когда-нибудь понадобится черновик — это отдельный
PR-based editorial workflow, а не третий флаг на документе.)

Одно не заменяет другое: отменённый выезд не «снимают с публикации», а
скрытый тур не становится отменённым.

**Почему:** иначе теряется история (отчёты и отзывы ссылаются на прошедшие и
отменённые выезды) и ломается сборка при попытке скрыть документ, на который
кто-то ссылается.

Из этого следуют два неочевидных решения:

* `scripts/sync-content.ts` **не** фильтрует по `isListed` — видимость применяется уже после
  нормализации, чтобы связи и валидация видели скрытые документы;
* видимость fail-closed: публикует только явный `isListed === true`. Документ,
  потерявший поле при миграции схемы или созданный через API, скрывается, а не
  становится внезапно публичным (`lib/cms/normalize.ts`, `flag()`).

## 9. `mikluha-commerce` — отдельный серверный сервис продажи

Всё, что продаёт поездку, живёт в одном небольшом сервисе `mikluha-commerce`:
заказы на выезды, места, данные пассажиров, замороженный коммерческий и
фискальный снимок заказа, ключ Refref и адаптер к нему, исполнение заказа
(fulfillment), решения о возвратах и **выключатель продаж** (закрыть приём
новых бронирований и оплат). Он заменяет `refref-mikluha-standin`, который
остаётся одноразовым инструментом canary Refref и в продажу не идёт.

**Хостинг.** Отдельное приложение Coolify на том же VPS, что и Refref, в своей
сети: с Refref сервис говорит только через публичный Business API, как любой
мерчант. Отдельный хост — позже, когда понадобится развести домены отказа;
сейчас это второй способ эксплуатации без решённой проблемы.

**Данные туристов.** Заказчик — всегда турист № 1, плюс телефон и email: заказчик, который сам не
едет, онлайн не оформляется (для ЕИС ему нужны свои документ, адрес и полномочия). Каждый турист — ровно то, что передаётся в
ЕИС «Электронная путёвка» (ПП РФ №417): ФИО, дата рождения, гражданство и документ, удостоверяющий
личность (вид, серия при наличии, номер). Ни даты выдачи, ни кем выдан, ни адреса, ни сканов. Пока
только совершеннолетние. Договор — оферта плюс Заявка на бронирование конкретного заказа, которая
показывается до оплаты и замораживается в момент оплаты. Оплаченная Заявка — это договор: хранится
3 года после окончания договора (ПП РФ №748: окончание поездки или возврат), остальные данные туристов — 90 дней (`commerce/README.md`).

**Хранилище.** Собственный Postgres-ресурс Coolify. Базу Refref не использовать:
данные пассажиров и заказов принадлежат Mikluha, Refref получает только то
подмножество коммерции и фискальных данных, которое нужно для оплаты и чека.
Postgres — единственный источник истины; Redis — только если сервису он
действительно понадобится, и никогда как хранилище данных.

**Резервные копии.** Та же уже проверенная машинерия, что у Refref:
ежечасный логический дамп **и** WAL/PITR (spool, отправка в S3, ежедневная
base backup с `pg_verifybackup`, мониторинг цепочки, проверка восстановления).
Отдельная цель и отдельный S3-префикс, шифрование отдельным ключом
`mikluha-recovery` (age). Ключ `refref-recovery` **не** переиспользуется:
потеря или ротация одного не должна затрагивать другой.

**Локализация (152-ФЗ).** И живая база, и резервные копии — в той же
российской инфраструктуре, что и Refref (VPS и S3 cloud.ru). Персональные данные
не уходят в иностранные сервисы, CI и логи.

**Код.** В этом репозитории, отдельным пакетом со своим `Dockerfile`: сервису
нужны те же выезды и цены из `content/`, а статическая сборка от него не
зависит. Секреты — только в Coolify, не в Git.

**Остановка продаж.** Выключатель сервиса — то действие, которым Refref-ранбук
`ops/runbooks/stop-sales.md` останавливает новые продажи. Он закрывает только
новые бронирования и оплаты; сверка, исполнение и возвраты по уже принятым
оплатам продолжают работать.

**Почему не managed Postgres.** У Refref уже работают и проверены PITR,
мониторинг и процедура восстановления. Managed-база добавила бы второй способ
эксплуатации, не решая текущей проблемы.

**Где живёт:** Linear ART-45 (решение), ART-46 (модель заказа и ПД), ART-47
(сервис и адаптер Refref).

## Решения по деплою (не архитектурные)

Контракт: сборка производит проверенный самодостаточный статический `/out`.
Каким именно механизмом Coolify его собирает и запускает — деталь реализации.

Сейчас выбран multi-stage `Dockerfile`, потому что он фиксирует toolchain
(Node, pnpm) и держит `nginx.conf` в Git рядом с кодом.
`nginx.conf` — не просто раздача файлов: `access_log off` (#5), брендированная
404 с корректным HTTP-статусом, кэширование локальной статики и security-заголовки.
Эти же свойства проверяет `scripts/healthcheck.ts` перед переключением трафика,
поэтому политика и её тест меняются одним коммитом.

Заменить Docker на Coolify Static/Nixpacks можно, если появится способ держать
конфигурацию web-сервера в репозитории, а не в UI.

### CMS publish: Simple Workflow + `skip_ci`, не Editorial Workflow

Кратко пробовали Sveltia Editorial Workflow (`publish_mode: editorial_workflow` +
`backend.squash_merges`): каждая запись получала свою ветку/PR и Publish был per-entry.
Отказались, потому что нужна была ровно обратная модель — один редактор делает Save по
нескольким разным записям в рамках сессии и хочет одну явную кнопку публикации на всё сразу,
а не отдельный Publish на каждую запись. Editorial Workflow такого batch/site-level publish не
предоставляет.

Текущая схема — Simple Workflow (без `publish_mode`) + `backend.skip_ci: true`: каждый Save
коммитит прямо в `main` с `[skip ci]` в сообщении (кроме удалений), Coolify игнорирует такие
push при автодеплое, а штатная кнопка тулбара «Опубликовать изменения» шлёт GitHub
`repository_dispatch` (штатное поведение Sveltia, когда Deploy Hook URL в браузере не настроен),
который принимает `.github/workflows/publish.yml` и релеит на Coolify Deploy Webhook —
не через git-коммит, поэтому работает даже если после последнего Save новых изменений не было.
Намеренно не через Deploy Hook URL в Settings редактора: это избавляет от хранения Coolify
credentials в браузере каждого редактора и от CORS-неопределённости browser→Coolify запроса.
Дока и настройка — `RUNBOOK.md` → «CMS: публикация (Simple Workflow + `skip_ci`)». Trade-off:
`skip_ci` — не настоящий draft, `main` уже содержит неопубликованные Save; ручной Coolify-deploy,
Save and Publish или любой не-skip коммит (например, Delete) может выпустить их раньше времени.
